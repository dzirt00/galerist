# Исполняемый план онлайн-MVP «Галериста»

Этот документ задаёт порядок следующих задач и их текущий статус. Продуктовые решения и общую архитектуру определяет `DEVELOPMENT_PLAN.md`, игровые правила — `RULES_SPEC.md`, канонические английские имена — `DOMAIN_GLOSSARY.md`. Этот план не переопределяет ни один из этих источников.

## Цель и границы

MVP — браузерная онлайн-игра с комнатами на 2–4 места. Все авторизованные пользователи видят список лобби; создатель может защитить вход паролем. Место занимает человек или бот. Состояние хранится на сервере, игрок может переподключиться и продолжить партию.

В MVP входят:

- magic-link авторизация;
- комнаты, список лобби, присоединение с необязательной защитой паролем и настройки таймера;
- серверное применение команд через `@galerist/game-engine`;
- Realtime-синхронизация и восстановление подключения;
- полный игровой интерфейс и финальный подсчёт;
- боты первого уровня и передача отключившегося места боту;
- desktop и горизонтальный планшет от 1024 px.

Локальная игра на одном устройстве, автоматический матчмейкинг, чат, рейтинг и сложный ИИ не входят в MVP. Оригинальные защищённые ассеты и оформление не используются.

## Статусы и выбор следующей задачи

Статус: `todo`, `in_progress`, `done` или `blocked`. Следующая учебная задача — первая строка `todo`, у которой завершены зависимости. Явно названный пользователем ID имеет приоритет.

Строка становится `done`, когда наблюдаемый сценарий работает через реальную границу слоя, добавлены необходимые тесты, выполнены указанные проверки, а в колонке «Доказательство» записаны файлы и сценарии. Подготовленный тип, компонент или helper без вызывающего пути остаётся `in_progress`.

## Обязательные архитектурные границы

1. PostgreSQL хранит авторитетный снимок и его версию; браузер не изменяет подтверждённый `GameState`.
2. Edge Function проверяет участника, `gameId`, `clientTurnId`, `stateVersion` и payload, затем атомарно вызывает движок и сохраняет snapshot с журналом событий.
3. Повторный `clientTurnId` идемпотентен и не применяет команду второй раз.
4. Клиент получает только `projectGameForViewer(state, playerId)` и `projectEventsForViewer`; скрытые данные не попадают в response, Pinia, props или DOM.
5. Личный черновик хода локален активному игроку. На сервер отправляется намерение, а не изменённый клиентом state.
6. Realtime сообщает о новой версии; при пропуске версий клиент заново загружает серверный snapshot.
7. Все прикладные таблицы защищены RLS; service role используется только внутри Edge Functions и не попадает в браузер.

### Согласованный контракт WEB-002

Архитектура согласована в учебном диалоге; готовность реализации и проверок отражена в строке WEB-002. Ниже собраны эскиз и уточнения пользователя.

1. Браузер через существующий клиент Supabase вызывает `create-game`: количество мест, ID запроса и необязательный пароль; токен сессии используется для авторизации. При сетевом повторе ID запроса сохраняется.
2. `create-game` проверяет токен через Supabase Auth и получает ID создателя из результата проверки. ID пользователя из тела запроса не считается доверенным.
3. Количество мест — целое число от 2 до 4 включительно. Пароль необязателен; если задан, содержит минимум 8 символов. Хеширование выполняется на сервере.
4. БД — авторитетный владелец данных. Одна транзакция сохраняет комнату, место создателя, связь «ID пользователя + ID запроса → ID комнаты» и хеш заданного пароля. Ошибка любой записи откатывает всю операцию.
5. Уникальность пары «ID пользователя + ID запроса» обеспечивается БД, включая одновременные запросы. Повтор возвращает прежнюю комнату, а не создаёт новую.
6. Безопасный DTO содержит ID комнаты, ID создателя, количество мест, занятые места и признак защиты паролем. Пароль, его хеш и service-role ключ клиенту недоступны; RLS включена на прикладных таблицах.
7. UI показывает загрузку, ошибку с повтором либо лобби после подтверждённого успеха. Свободных мест — выбранное количество минус одно.
8. Движок не вызывается, `GameState` и игровые события не создаются. Список лобби и присоединение относятся к WEB-003, боты и настройки таймера — к WEB-004, запуск — к WEB-005. В WEB-002 длительность таймера не назначается; приглашения не создаются.

Ручные прогоны архитектуры (не подтверждение работы реализации): пользователь `user-3`, запрос `request-5`, 3 места → комната `game-8`, участник `user-3` в `game-8`, одно занятое и два свободных места. Повтор `user-3 + request-5` возвращает `game-8`, новых комнат нет. Количество мест 5, отсутствие авторизации или пароль из 7 символов → ошибка без новых записей. Без пароля создание разрешено; пароль из 8 символов проходит проверку длины.
