# Протокол работы агента

Этот документ связывает инструкции проекта, предметные источники, skills и проверки в один цикл работы. Он не определяет игровых правил и не заменяет `AGENTS.md`, `RULES_SPEC.md` или `DOMAIN_GLOSSARY.md`. Указания пользователя определяют цель и разрешённые действия. Команды проверки автоматически выполняются в CI; остальные пункты этого протокола соблюдает агент.

## Выбор режима

| Запрос | Процесс | Результат |
| --- | --- | --- |
| «Давай задачу», пользователь пишет реализацию | `.agents/skills/galerist-task-cycle/SKILL.md` | Одна задача → эскиз и ручной прогон → явное принятие архитектуры → реализация пользователя → проверка, тесты и статусы |
| Реализовать или исправить игровое правило | `.agents/skills/galerist-rule-implementation/SKILL.md` | Один наблюдаемый срез через публичную точку входа движка |
| Проверить соответствие правилам | `.agents/skills/galerist-rules-audit/SKILL.md` | Доказательства и расхождения без изменения файлов, если исправления не запрошены |
| Изменить интерфейс или инфраструктуру | `AGENTS.md` и этот протокол | Изменение в границах запроса и применимые проверки |

Читать выбранный skill перед его применением. Для первоначальной выдачи учебной задачи соблюдать быстрый выбор из `AGENTS.md`: не запускать проверки, не читать полный diff и не проводить глубокий аудит. Этот этап завершается карточкой задачи; критерии готовности реализации ниже к нему не относятся.

## Начало работы

1. Зафиксировать цель и наблюдаемый критерий приёмки. Для изменения правила указать его ID и границы среза; для остальных задач не придумывать ID игрового правила.
2. Проверить `git status --short`. Существующие изменения считать работой пользователя; не сбрасывать, не перезаписывать и не включать в коммит без соответствующего запроса. Читать diff только затронутых задачей файлов по необходимости.
3. Найти нужную запись спецификации, связанные ADR/DATA и термины словаря. Читать относящиеся к задаче участки через `rg`, не обходить весь реестр без запроса на полный аудит.
4. Для реализации определить публичную точку входа, владельца каждого эффекта и интеграционный сценарий до добавления helper. Проверить существующие функции и переиспользовать их.
5. При `needs_decision` или `needs_data` назвать конкретное отсутствующее решение или данные. Не реализовывать зависящее от них поведение; продолжать независимую часть задачи, если она есть.

## Изменение и проверка

- Игровые расчёты и переходы состояния находятся в `packages/game-engine`; входное состояние сохраняется неизменным.
- Новые публичные имена сверяются со словарём. Наличие helper или unit-теста само по себе не доказывает реализацию правила.
- Проверка правила проходит через его публичную команду или оркестратор. Она подтверждает результат, применимый отказ или границу, неизменяемость и относящиеся к срезу события и публичную проекцию.
- В учебном режиме агент соблюдает границы skill: не пишет за пользователя production-код и не пропускает принятие архитектуры.
- Перед завершением просмотреть собственные изменения на случай несвязанного кода, потери пользовательских правок и расхождения с источниками.

| Изменённая область | Обязательная команда |
| --- | --- |
| Движок | `npm run verify:engine` |
| Интерфейс | `npm run verify:web` |
| Обе области или общая конфигурация их проверок | `npm run verify` |
| Только документация | Проверить diff, ссылки и согласованность инструкций; сборку и тесты без отдельной причины не запускать |

Команды определены в `package.json`. `verify:engine` включает проверку типов исходников и тестов, тесты и сборку движка; `verify:web` — lint, тесты и сборку интерфейса. `.github/workflows/ci.yml` запускает `npm run verify` для pull request и push в `main`. Общий `verify` также выполняет `verify:harness`: тесты инструментов, статические ограничения архитектуры и валидацию набора сценариев. После изменения зависимостей или импортов движка и приложений дополнительно запускать `npm run check:architecture`.

Автоматические ограничения и порядок оценки поведения агента описаны в [harness/README.md](harness/README.md). `npm run eval:harness -- --validate-suite` проверяет только структуру сценариев; оценка агента требует отдельного прогона и отчёта ревьюера с доказательствами.

Если проверка падает, установить связь ошибки с изменением. Исправить вызванную задачей ошибку и повторить применимую проверку. Для существующей или внешней ошибки привести конкретное доказательство и указать, какая проверка остаётся непройденной. Отсутствие запуска, тайм-аут или частичный вывод не считать успехом.

## Готовность и отчёт

Реализация готова, когда согласованный результат доступен через рабочий путь, применимые проверки прошли, а затронутая запись правила, трассировка и строка матрицы отражают фактический объём. Для частичного среза сохранять `partial`; не присваивать всему правилу `yes` по одному готовому сценарию. Статус `spec: approved` требует явного решения пользователя.

В итоговом ответе указать:

- что изменилось и какой критерий приёмки выполнен;
- какие команды завершились успешно, какие упали или не запускались;
- оставшийся блокер или непроверенную часть, если они есть.

Не объявлять весь рабочий каталог проверенным, если проверялась только одна область. Коммит, push и публикация не следуют автоматически из завершения локальной задачи.

## Передача незавершённой работы

При необходимости сохранить контекст между сессиями использовать `TASK_HANDOFF.md` в корне проекта. Не создавать файл для каждого короткого запроса и не перезаписывать существующую запись о другой задаче. Перед продолжением сверять запись с текущим кодом и git status: она описывает прогресс, но не является источником игровых правил или новых разрешений.

Шаблон:

```markdown
# Передача задачи

- Цель и критерий приёмки:
- Режим и ID правила, если применимо:
- Этап учебного цикла; где явно принята архитектура, если применимо:
- Завершено (файлы, точки входа, тесты):
- Проверки (команда, результат, на каком этапе изменений выполнена):
- Незавершено и конкретный блокер:
- Следующий шаг:
- Существующие изменения пользователя, которые нужно сохранить:
```

Если подтверждения принятия архитектуры нет, не отмечать её принятой. После новых изменений ранее успешные проверки не доказывают готовность изменённого кода.
