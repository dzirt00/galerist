# Правило готово только в рабочем сценарии

`RULES_SPEC.md` — источник истины. Не угадывать `needs_decision` и `needs_data`: первое требует решения по механике, второе — проверенных справочных данных.

Реализовывать одно правило или один наблюдаемый срез правила за цикл:

1. До написания helper определить рабочий путь: какая публичная команда или setup-оркестратор вызывает механику, какие поля итогового `GameState` меняются и что должен увидеть следующий этап.
2. Проверить существующий код и переиспользовать подходящие чистые функции. Новую чистую функцию добавлять только для расчёта, который нужен текущему срезу; не создавать набор заготовок для будущей интеграции.
3. Сразу подключить расчёт к рабочему пути и вернуть новое неизменяемое состояние. Не вводить универсальную командную абстракцию, если текущему срезу достаточно существующего API.
4. Добавить доменные события, runtime-валидацию внешнего ввода или восстановленного состояния и публичную проекцию скрытых данных там, где они относятся к срезу. Неприменимые пункты явно отметить в результате.
5. Добавить интеграционный тест через публичный API движка: положительный сценарий, граничный или ошибочный сценарий и проверку неизменяемости. Unit-тест чистого расчёта добавлять, когда в нём есть самостоятельное нетривиальное поведение.
6. Запустить typecheck и тесты пакета движка.
7. Обновить только запись затронутого правила, её трассировку и соответствующую строку матрицы. `implementation: yes` и `tests: yes` допустимы только когда весь контракт правила доступен через рабочий путь и проверен интеграционно. Изолированный helper означает не более `partial`. Не менять `spec` на `approved` без явного решения пользователя.

Если пользователь пишет код сам, использовать `galerist-task-cycle`: не изменять его реализацию и не создавать коммит без просьбы.
