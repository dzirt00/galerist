# Практика архитектуры перед реализацией

Этот процесс применяется к учебным задачам из `galerist-task-cycle`. Его цель — тренировать не только локальные алгоритмы, но и композицию существующих функций без повторной реализации их логики.

## 1. Сначала архитектурный эскиз

После получения задачи пользователь присылает не код, а короткий эскиз:

```text
Публичная точка входа:
Владелец каждого эффекта:
Читает из состояния/команды:
Вызывает существующие функции:
Новый чистый расчёт, если нужен:
Записывает в новое состояние:
Создаёт события:
Ошибки и атомарность:
Не делает:
```

`Владелец каждого эффекта` фиксирует, какая единственная функция считает или применяет оплату, награду, перемещение либо другой игровой эффект. Внешний слой не повторяет её условия и формулы.

Для задачи онлайн-MVP, проходящей через сервер, использовать адаптированный шаблон:

```text
Пользовательский сценарий:
Авторитетный владелец состояния:
Граница доверия:
Запрос браузера:
Сервер проверяет:
Вызывает движок:
Атомарно сохраняет:
Возвращает проекцию/события:
Локальное UI-состояние:
Повтор, конфликт версии и ошибка:
Не делает:
```

Полный `GameState` и service-role доступ остаются на сервере. Браузер отправляет намерение с `gameId`, `clientTurnId`, `stateVersion` и payload; сервер проверяет участника и версию, вызывает движок, атомарно сохраняет snapshot и журнал, затем возвращает публичную проекцию или события. Компоненты хранят только UI-состояние и данные проекции. Для чисто UI-задачи эскиз может начинаться с уже существующего публичного DTO и не должен изобретать владельца полного состояния.

## 2. Ручной прогон

К эскизу добавить один конкретный пример:

```text
До: важные поля входа.
Вызовы: какие функции и что они возвращают.
После: какие поля нового состояния изменились.
События: точный порядок и значения.
```

Пример должен проходить через весь заявленный срез. Числа и идентификаторы нужны только там, где помогают обнаружить двойное применение, потерю результата или неверный порядок.

## 3. Минимальные сценарии до кода

Назвать три сценария без написания тестов:

1. Основной успешный путь.
2. Один граничный случай.
3. Один отказ, который обязан оставить вход неизменным.

## 4. Архитектурный шлюз

Ассистент сверяет эскиз с существующим кодом и проверяет:

- у каждого эффекта один владелец;
- готовая функция вызывается, а не переписывается;
- результат каждого вызова передаётся следующему уровню;
- публичная команда собирает новый `GameState` и события, но не дублирует доменный расчёт;
- раздел `Не делает` задаёт ясную границу ответственности;
- отказ не оставляет частичных эффектов.

Для онлайн-среза дополнительно проверить:

- UI не вычисляет доступность по скопированным игровым формулам, если её определяет команда или публичная проекция;
- скрытые данные не проходят в props, DOM, сообщения об ошибке или журнал событий;
- service-role ключ и полный `GameState` не попадают в браузер;
- сервер проверяет участника, `stateVersion`, `clientTurnId` и payload по контракту выбранного среза;
- повтор с тем же `clientTurnId` идемпотентен, а snapshot и журнал меняются одной транзакцией, когда срез отправляет игровую команду;
- локальный optimistic update не изображает успешную команду до серверного подтверждения;
- тест проверяет пользовательское действие и наблюдаемый результат, а не внутреннюю структуру компонента.

Если есть проблема, ассистент сообщает только один ближайший архитектурный блокер. Пользователь исправляет псевдокод, а не реализацию.

К написанию кода переходят только после явной фразы ассистента:

> Архитектура принята — переходи к реализации.

## 5. После реализации

Перед ревью пользователь сравнивает код с принятым эскизом и кратко отмечает:

- какие существующие функции были переиспользованы;
- где находится единственный владелец каждого эффекта;
- пришлось ли отойти от эскиза и почему.

Если реализация требует неожиданного перераспределения ответственности между модулями, код не наращивается поверх проблемы: сначала снова согласуется архитектурный эскиз.
