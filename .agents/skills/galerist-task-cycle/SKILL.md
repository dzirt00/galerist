# Один цикл — один наблюдаемый вертикальный срез

`RULES_SPEC.md` — источник истины для поведения, `DOMAIN_GLOSSARY.md` — источник канонических английских имён, `DEVELOPMENT_PLAN.md` — источник продуктовых и архитектурных решений, `WEB_MVP_PLAN.md` — источник порядка и готовности срезов онлайн-MVP. План реализации не переопределяет правила движка или продуктовые решения.

Читать только нужную запись источника, её прямые зависимости, релевантные термины словаря, сигнатуры вызываемого API, код и тесты через поиск по ID. Не угадывать `needs_decision` и `needs_data`. Игровая логика остаётся в `packages/game-engine`, переходы состояния неизменяемы. В онлайн-сценарии полный `GameState` хранится на сервере: браузер отправляет намерение, сервер проверяет его и вызывает движок, а клиент получает только публичную проекцию.

Для каждой учебной задачи полностью прочитать и соблюдать:

- [практику архитектуры](references/architecture-practice.md);
- [учебный контракт](references/learning-contract.md).

## Когда пользователь просит задачу

1. Если указан ID правила, проверить его готовность в `RULES_SPEC.md`. Если указан `WEB-*`, проверить строку и зависимости в `WEB_MVP_PLAN.md`. Иначе, когда все правила MVP движка завершены, выбрать первую строку `todo` web-плана с завершёнными зависимостями; незавершённое правило движка выбирать только когда пользователь явно возвращает работу к движку.

2. Выбирать минимальный наблюдаемый срез, который сразу проходит через публичную команду/оркестратор движка либо через реальную границу браузер → сервер → движок → проекция. Не выдавать изолированный helper, store, Edge Function или визуальный компонент, который рабочий путь пока не использует.

3. Определить место среза в сценарии:

  - публичную точку входа;
  - входные данные;
  - существующие функции, которые нужно переиспользовать;
  - изменение итогового `GameState`;
  - данные для следующего этапа;
  - владельца каждого игрового эффекта.

  Для среза онлайн-MVP дополнительно определить авторитетного владельца полного `GameState`, границу доверия, серверные проверки и транзакцию, публичную проекцию, UI-состояние формы и видимый результат. Браузер не должен получать скрытое состояние, service-role доступ или повторять правила движка.

4. Задача должна быть достаточно мала, чтобы архитектурный псевдокод занимал примерно 5–12 строк. Если сначала требуется перераспределить ответственность существующих модулей, ассистент делает это сам либо выбирает другую учебную задачу.

5. Дать одну карточку задачи:

  - ID и цель;
  - контракт расчёта;
  - рекомендуемые имена из `DOMAIN_GLOSSARY.md`;
  - точку интеграции;
  - готовые функции, которые следует вызвать;
  - функции и расчёты, которые нельзя повторять;
  - затрагиваемые поля состояния;
  - события и проекцию;
  - 2–4 критерия приёмки.

  Для `WEB-*` задачи вместо контракта нового доменного расчёта указать пользовательский сценарий, запрос браузера, серверные проверки и транзакцию, вызываемые API движка, публичный DTO/события, состояния сети/ошибки/повтора и селекторы наблюдаемого результата. Для чисто UI-задачи начинать с уже готовой проекции. Не придумывать ID игрового правила для продуктовой работы.

6. Попросить пользователя прислать только архитектурный эскиз и ручной прогон по шаблону из `references/architecture-practice.md`. Не просить писать реализацию.

7. Если нового термина нет и его смысл неоднозначен, сначала запросить решение пользователя.

## Когда пользователь присылает архитектурный эскиз

1. Сверить эскиз с реальным вызывающим путём и контрактами названных функций. Для `WEB-*` среза также сверить его со строкой плана, продуктовым решением в `DEVELOPMENT_PLAN.md`, серверной границей и формой публичной проекции.

2. Проверить:

  - у каждого игрового эффекта один владелец;
  - готовые функции вызываются вместо повторения их логики;
  - результат каждого вызова передаётся следующему уровню;
  - публичная команда собирает новый `GameState` и события, но не повторяет доменный расчёт;
  - указаны изменяемые поля нового состояния;
  - указан точный порядок событий;
  - отказ не оставляет частичных эффектов;
  - раздел `Не делает` фиксирует границу ответственности;
  - ручной прогон согласуется с псевдокодом.

  Для онлайн-среза проверить, что полный `GameState` остаётся на сервере, команда валидирует участника, `stateVersion`, `clientTurnId` и payload, изменение snapshot и журнала атомарно, повтор идемпотентен, а браузер читает проекцию и не маскирует ошибку локально «предсказанным» успехом. Для чисто UI-среза достаточно доказать работу от существующего публичного DTO.

3. Если есть проблема, назвать только один ближайший архитектурный блокер. Объяснить нарушенную ответственность или потерянный поток данных и попросить исправить только эскиз. Не обсуждать синтаксис и не предлагать реализацию.

4. Если блокеров нет, явно написать:

   **Архитектура принята — переходи к реализации.**

5. После принятия кратко повторить согласованную цепочку вызовов и границы ответственности.

6. Если пользователь прислал код до принятия архитектуры, не начинать полноценное ревью. Сначала восстановить из решения архитектурный эскиз и пройти этот этап.

## Когда пользователь сообщает, что код готов

1. Убедиться, что архитектурный эскиз был принят.

2. Попросить пользователя кратко указать:

  - какие существующие функции переиспользованы;
  - где находится единственный владелец каждого эффекта;
  - пришлось ли отойти от эскиза и почему.

3. Посмотреть `git diff`, запись правила либо строку онлайн-плана, вызывающий рабочий путь, реализацию и релевантные тесты. Не затирать изменения пользователя.

4. Сначала проверить соответствие принятому эскизу:

  - вызывается ли заявленный расчёт;
  - не продублирована ли его логика;
  - передаётся ли результат дальше;
  - меняются ли правильные поля нового `GameState`;
  - сохраняется ли вход.

5. Затем проверить контракт helper, типы, крайние случаи и соответствие новых имён словарю. Непонятное новое имя объяснить и предложить конкретную замену. Наследованные имена вне текущего среза не делать блокером.

6. Где применимо, проверить runtime-валидацию, доменные события и отсутствие скрытых данных в публичной проекции.

7. Если обнаружено расхождение с архитектурой, сначала назвать один ближайший блокирующий дефект. Не выдавать сразу каскад зависимых ошибок. Следовать учебному контракту: не менять production-код пользователя и не завершать за него текущую реализацию.

8. Когда рабочий путь готов, написать или дополнить тесты наблюдаемого сценария. Для движка проверять публичный API; для онлайн-среза — серверную авторизацию/версию/идемпотентность/атомарность по применимости, границу проекции и пользовательский результат; для чистого UI — действие, видимый результат и ошибку без ложного успеха. Unit-тесты добавлять для самостоятельной логики helper. Если тест выявил дефект, сохранить полезный падающий тест и не объявлять срез завершённым.

9. Запустить проверки, указанные в строке `WEB_MVP_PLAN.md`, и обязательные команды из `AGENTS.md` для реально изменённых областей. Для чистого движка использовать `npm run verify:engine`, для чистого интерфейса — `npm run verify:web`, для общей конфигурации или нескольких областей — `npm run verify`; отдельно выполнить предусмотренные срезом проверки Edge Functions, транзакций и RLS. Если запуск невозможен, явно сообщить об этом и не считать проверки пройденными.

10. Для движка обновить только запись правила, её трассировку и соответствующую строку матрицы. Для онлайн-MVP обновить только статус и доказательство выбранной строки `WEB_MVP_PLAN.md`; не менять `RULES_SPEC.md`, если игровой контракт не изменился. Изолированный helper, серверный endpoint или компонент остаётся `partial`/`in_progress`; `yes`/`done` допустим только для полностью доступного и проверенного контракта. Не менять `spec` на `approved` без явного решения пользователя.

При изменении интерфейса выполнять проверки из `AGENTS.md`. Не создавать коммит без запроса.
