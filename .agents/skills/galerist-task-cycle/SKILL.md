# Один цикл — один наблюдаемый вертикальный срез

`RULES_SPEC.md` — источник истины. Читать только нужную запись, связанные ADR/DATA, код и тесты через поиск по ID. Не угадывать `needs_decision` и `needs_data`. Игровая логика остаётся в `packages/game-engine`, переходы состояния неизменяемы.

## Когда пользователь просит задачу

1. Если указан ID, проверить его готовность. Иначе выбрать небольшой следующий блок с `spec: approved` без блокеров. Выбирать не отдельный helper, а минимальный наблюдаемый срез, который можно сразу включить в существующую команду или оркестратор.
2. Сначала определить место среза в общем сценарии: публичная точка входа, необходимые входные данные от предыдущего этапа, изменение итогового `GameState` и данные для следующего этапа. Не предлагать абстракции и функции, которые текущий рабочий путь пока не вызывает.
3. Дать одну карточку задачи: ID и цель; точный контракт чистого расчёта; точка интеграции; затрагиваемые поля состояния; ожидаемые события и проекция, если применимы; 2–4 критерия приёмки, включая интеграционный результат, граничный случай и неизменяемость; что прислать для проверки.
4. Пользователь пишет реализацию. Не менять её и не выдавать готовый патч без просьбы. На вопросы отвечать в границах текущего среза.

## Когда пользователь сообщает, что код готов

1. Посмотреть `git diff`, запись правила, вызывающий рабочий путь, реализацию и релевантные тесты. Не затирать изменения пользователя.
2. Сначала проверить интеграцию: вызывается ли новый расчёт из заявленной точки входа, меняет ли правильные поля нового `GameState`, передаёт ли данные дальше и сохраняет ли вход. Затем проверить контракт helper, типы и крайние случаи.
3. Где применимо, проверить runtime-валидацию, доменные события и отсутствие скрытых данных в публичной проекции. Неприменимые пункты отметить как таковые.
4. Сначала назвать конкретные дефекты с местом и ожидаемым поведением. Если нужен патч реализации, предложить пользователю короткий следующий шаг; самому менять его код только по просьбе.
5. Когда рабочий путь готов, написать или дополнить интеграционные тесты через публичный API движка. Unit-тесты добавлять для самостоятельной логики helper. Если тест выявил дефект, сохранить полезный падающий тест и не объявлять срез завершённым.
6. Запустить `npm run typecheck --workspace=@galerist/game-engine` и `npm run test --workspace=@galerist/game-engine`. Если запуск невозможен, явно сообщить об этом и не считать проверки пройденными.
7. Обновить только запись правила, её трассировку и соответствующую строку матрицы. Изолированный helper остаётся `partial`; `yes` допустим только для полностью доступного и интеграционно проверенного контракта. Не менять `spec` на `approved` без явного решения пользователя.

При изменении интерфейса выполнять проверки из `AGENTS.md`. Не создавать коммит без запроса.
