# Проверки архитектуры и оценка агента

`npm run verify:harness` запускает тесты проверяющих инструментов, анализ архитектуры текущего проекта и проверку структуры набора сценариев. Эта команда включена в `npm run verify`, поэтому уже существующий CI выполняет её перед проверками движка и интерфейса.

## Архитектура

`npm run check:architecture` анализирует AST TypeScript/JavaScript и script-блоки Vue в `packages/game-engine/src` и `apps`. Комментарии и строковые примеры не считаются кодом. Ошибка содержит файл, строку и ID ограничения.

| ID                     | Ограничение                                                                                        |
| ---------------------- | -------------------------------------------------------------------------------------------------- |
| `engine-boundary`      | Относительные зависимости движка остаются внутри его `src`                                         |
| `engine-dependency`    | Внешняя зависимость движка разрешена только для детерминированного хеширования через `node:crypto` |
| `engine-crypto`        | Из `node:crypto` разрешён только именованный импорт `createHash`, включая alias                    |
| `public-engine-api`    | Приложения обращаются к движку через `@galerist/game-engine`, без внутренних путей                 |
| `static-import`        | Пути импортов, реэкспортов, require и dynamic import должны быть строковыми литералами             |
| `deterministic-engine` | В движке запрещены прямые обращения к случайности, часам, браузеру, окружению и сетевому вводу     |

Проверка консервативно запрещает вычисляемый доступ, alias и деструктуризацию всего `Math`, а также ambient-имена вроде `Date` даже при локальном объявлении. Это ограниченный статический контроль, а не анализ всех потоков данных: произвольные зависимости, переданные через аргументы, и исполнение кода через eval требуют ревью. Он не доказывает неизменяемость, отсутствие игровой логики в UI, корректность скрытых данных, каноничность имён или интеграцию правила. Эти свойства проверяются через спецификацию, ревью и интеграционные тесты. Новую допустимую внешнюю зависимость движка следует явно обосновать и обновить политику и её тесты в той же задаче.

## Прогон сценариев

[scenarios.json](scenarios.json) содержит восемь сценариев с входным запросом, подготовкой и отдельными критериями. Они оценивают учебный цикл, работу с блокерами, аудит helper, сохранение пользовательского кода, реакцию на архитектурное нарушение и падающие проверки, восстановление контекста.

1. Использовать отдельную одноразовую копию проекта для каждого независимого сценария. Не создавать падающие тесты или нарушения в рабочем каталоге пользователя. Для сценария-продолжения сохранить историю предыдущего этапа.
2. Ревьюер готовит описанное исходное состояние, сохраняет исходный diff и точный prompt, затем передаёт запрос агенту. Набор сценариев не запускает агента автоматически.
3. Сохранить переписку, журнал инструментов, исходный и итоговый diff, результаты команд. Ревьюер оценивает каждый критерий по этим артефактам, включая действия агента, а не только финальный ответ.
4. Создать пустой отчёт: `npm run eval:harness -- --template harness-report.json`. Команда отказывается перезаписывать существующий файл.
5. Заполнить `agent` (модель и настройки), `reviewer`, `evaluatedAt` (ISO-дата); для каждого сценария — `artifacts`, для каждого критерия — `passed` и `evidence` с путём к артефакту и конкретным фрагментом или строкой. Невыполненный критерий остаётся `null` и не проходит gate. После заполнения убрать личные данные из публикуемых артефактов.
6. Выполнить `npm run eval:harness -- harness-report.json`. Код 0 означает, что полный отчёт содержит успешные вердикты ревьюера по всем критериям. Любой провал, пропуск, неизвестный или повторный ID, отсутствие доказательства дают код 1.

Валидатор проверяет полноту и вердикты отчёта; он не читает артефакты и не устанавливает истинность оценки ревьюера. Успешный `--validate-suite` подтверждает только структуру сценариев. В CI нет утверждения, что поведение агента прошло оценку. Для сравнения версий агента использовать одинаковые исходные состояния и prompts и хранить отдельные отчёты; менять критерии после просмотра результата нельзя.

Синтетические отчёты в unit-тестах проверяют валидатор и не являются результатами оценки агента.
