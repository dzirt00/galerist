# Проверка миграций, RLS и создания комнаты WEB-001/002

## Целевой SQL-прогон WEB-018

`npm run test:db -- --room-restrictions` применяет все миграции в том же
изолированном контейнере и запускает `room-restrictions.sql` и
`room-restrictions.mjs`. Проверяются статусы комнаты, новый JSON-результат
`create_game`, повтор requestId, ограничения создания/входа, закрытая история,
сохранность DTO таймера, запрет исполнения клиентскими ролями и откат создания.
Два соединения проверяют конкурентные одинаковые/разные requestId и оба порядка
создания и входа. Для последних сценариев наблюдается настоящая advisory lock
первой транзакции до отправки второго запроса.

Это частичная проверка WEB-018 на уровне PostgreSQL. Она не проверяет Auth,
Edge Functions, UI, доставку Realtime или будущие команды запуска, закрытия
и передачи роли. Статусы GAME_STARTED/CLOSED задаются тестовыми UPDATE.
Общий `npm run test:db` также запускает эти проверки после прежних сценариев.
Прежние fixtures изолированы через savepoint; создание читает `gameId` из JSON,
а исторические комнаты не остаются открытыми при создании следующего лобби.

## Возврат в своё лобби WEB-018

Миграция `20261105000000_get_own_lobby.sql` добавляет server-only чтение
`get_own_lobby(gameId, userId)` под блокировками пользователя и комнаты.
`own-lobby.sql` включён в общий и целевой прогоны: безопасный DTO, полный
защищённый состав, повтор без записей, чужой/прежний владелец, отсутствие
участия, CLOSED/GAME_STARTED и запрет исполнения клиентскими ролями.
Список `get_game_list` исключает закрытые комнаты и начатые партии.

`room-restrictions.mjs` также проверяет чтение возврата против изменений
статуса/владельца в обоих порядках. Изменения моделируются тестовыми UPDATE
под блокировкой; это не реализация и не проверка будущих start/leave-команд.

## Общий прогон

Из корня репозитория: `npm run test:db`. Нужен запущенный Docker с доступом
текущего пользователя к daemon; при первом запуске загружается `postgres:17-alpine`.

Команда создаёт отдельный временный контейнер без открытых портов, подключения
к облачной БД или монтирования файлов. После тестов контейнер и его тома удаляются.
Миграции из `supabase/migrations` выполняются без изменений. Ошибка SQL или
проверки завершает команду с ненулевым кодом.

Для Realtime-блока WEB-004 `realtime-fixture.sql` создаёт минимальный локальный
контракт `realtime.messages`, `realtime.topic()` и `realtime.send()`. Это не
Supabase Realtime: fixture сохраняет аргументы отправки в таблицу в той же
транзакции, но не открывает WebSocket и не доставляет сообщения браузерам.
`lobby-realtime.sql` проверяет настоящий триггер готовности, отсутствие сигнала
при неизменном значении, приватный topic/payload/event, откат уведомления,
RLS для обоих участников/чужой комнаты/постороннего/anon и сохранение запрета
прямого чтения `game_players`. После миграции INSERT/UPDATE также проверяются
сигнал при создании места и входе участника, отсутствие лишнего сигнала при
повторном входе или отказе заполненной комнаты и откат вставки вместе с сигналом.
Политика проверяется с фильтром запрошенного
topic, как при авторизации канала; фактическая доставка и поведение сервиса
Supabase требуют отдельного прогона двух клиентов.

Проверяются автоматическое создание профиля для двух новых пользователей,
значение `created_at`, включённый RLS, отсутствие анонимного и чужого чтения,
доступ к собственной строке, запрет клиентской вставки и подтверждённый внешний
ключ с `NO ACTION`.

Для WEB-002 проверяются вызов `create_game` от `service_role`, создание комнаты
на 2/3/4 места и места создателя, сохранение необязательного хеша, повтор
запроса и независимость одинаковых ID запросов у разных пользователей.
Неверная вместимость, отсутствующие ID и неизвестный создатель отклоняются.
Искусственная ошибка последней вставки подтверждает откат комнаты, места и хеша.
Для `anon` и `authenticated` проверены скрытие строк четырёх таблиц через RLS,
запрет прямой вставки комнаты и запрет вызова функции.

Два независимых соединения отправляют один запрос параллельно. Тестовый триггер
задерживает вставку комнаты, чтобы вызвать перекрытие запросов. Проверяются
одинаковые возвращённые ID и ровно один комплект сохранённых записей.
Для этой проверки fixtures фиксируются только во временном контейнере;
затем контейнер удаляется целиком.

`bootstrap.sql` — тестовое окружение: минимальные `auth.users`, `auth.uid()`
и роли `anon`/`authenticated`, а также серверная роль `service_role` с `BYPASSRLS`.
Права на таблицы выдаются клиентским ролям специально,
чтобы проверить именно RLS. Это не полная установка Supabase Auth и не миграция
для Dashboard. Тест не проверяет выдачу JWT, PostgREST или настройки прав
облачного проекта. Отправка magic link, возврат, создание профиля новым
пользователем и восстановление сессии дополнительно проверяются вручную.
Хеши в тестах — условные строки: проверка длины пароля, настоящее хеширование,
проверка токена, безопасный DTO и сценарий браузера WEB-002 пока не проверяются.
