# Диагностика задержки game-list

Обработчик вызывает `get_game_list()` одним RPC и сохраняет прежний JSON-ответ.
SQL возвращает счётчики и признак пароля в одном снимке данных; функция
доступна только `service_role`, проверка пользовательской сессии остаётся в Edge Function. Для каждого вызова пишет
структурированные JSON-сообщения через `console.info`:

- `game-list.request-timing`: `method`, `status`, `authMs` — ожидание
  `auth.getUser`, `totalMs` — время с входа в обработчик до подготовки ответа.
  `authMs: null` означает, что проверка сессии не запускалась.
- `game-list.db-timing`: `roomCount` — число прочитанных комнат,
  `queryCount` — число завершившихся/отклонённых обращений к PostgREST,
  `queries` — последовательность `{table, durationMs}`, `totalMs` — время
  блока чтения списка после Auth. При ошибке остаются замеры выполненной части;
  `roomCount: null` означает, что список ещё не был успешно прочитан.

Все длительности — в миллисекундах, включая ожидание сети и разбор ответа SDK.
Это не чистое время SQL. Не складывать оба `totalMs`: блок БД входит в общее
время запроса. Время запуска runtime и путь браузер → gateway → обработчик
в эти замеры не входят. Логи не содержат ключей, токенов, ID комнат и паролей.
В остальных Edge Functions эти замеры по умолчанию выключены.

## Облачный замер

Сначала выполнить SQL из `supabase/migrations/20261028000000_get_game_list.sql`
в SQL Editor нужного проекта (в транзакции BEGIN / COMMIT). Это создаёт
SQL-функцию и ограничивает её вызов серверной ролью. Затем опубликовать
обновлённый обработчик из корня репозитория:

```powershell
npx supabase functions deploy game-list --project-ref mrbrfnxpepogfhmwvdbx --no-verify-jwt
```

Проверка пользовательского токена остаётся внутри `withAuthenticatedRequest`.
Без предварительной миграции новый обработчик вернёт 500. В браузере открыть DevTools → Network, нажать «Обновить»
в списке комнат три раза, каждый раз дождавшись результата. Записать время
каждого GET game-list и отдельно OPTIONS, если он присутствует.

В Supabase Dashboard → Edge Functions → game-list → Logs найти два события
для каждого GET. При одновременных запросах сопоставлять их по `execution_id`
в метаданных выполнения, а не только по близким отметкам времени. Сохранить
также регион выполнения из метаданных.

Большой `authMs` указывает на задержку проверки сессии. Большая сумма
`queries[].durationMs` — на задержку последовательных обращений к PostgREST;
После оптимизации ожидается `queryCount: 1` и единственная запись
`{table: "get_game_list", durationMs: ...}` независимо от числа комнат. Если браузер ждёт существенно дольше серверного
`totalMs`, оставшуюся задержку нужно искать вне измеренного обработчика.

## Локальная проверка

Команды запуска Postman simulation и HTTP-тестов описаны в
`postman/mocks/web003-supabase/README.md`. HTTP-тест проверяет сохранность DTO,
тайминги успешного и пустого списка, OPTIONS, ошибок RPC, повреждённых DTO и постоянного числа обращений, а также
отсутствие секретов и ID комнат в диагностике. Локальная simulation
не измеряет производительность облачной базы.
