# Реестр правил проекта «Галерист»

> Статус документа: черновая формализация источника. Правило считается согласованным только после смены статуса `draft` на `approved`.

## 1. Назначение и границы

Этот файл содержит проверяемые контракты игрового движка. Он не воспроизводит текст или оформление исходного руководства. Формулировки ниже являются кратким техническим пересказом механик.

Источником служит русское руководство к настольной игре, разделы «Подготовка к игре» — «Финальный подсчёт» и «Одиночная игра». Номера страниц указаны по печатной нумерации источника.

В продуктовый MVP входят партии на 2–4 места, занятые людьми или ботами. Официальный одиночный вариант с нейтральным соперником вынесен в отдельный отложенный раздел и не должен смешиваться с режимом «один человек против ботов».

## 2. Статусы и трассировка

Каждая запись содержит:

- `spec`: `draft`, `needs_decision`, `needs_data`, `approved` или `deferred`; `needs_data` означает отсутствие проверенных справочных данных при отдельно согласуемой механике;
- `implementation`: `no`, `partial` или `yes`;
- `tests`: `no`, `partial` или `yes`.

После появления реализации в поле статуса добавляется ссылка на модуль, а после появления тестов — имя теста или сценария. Значение `partial` означает, что существующий код совпадает лишь с частью контракта и ещё не реализует правило целиком.

События перечислены как предполагаемые доменные имена. Они не фиксируют TypeScript API до отдельного согласования модели `GameEvent`.

### ADR-001 — Seed и выбор первого игрока минимального движка

- **Согласованная часть:** одинаковые seed, порядок игроков и версии правил, компонентов и алгоритма дают одинаковый результат случайной подготовки. При одинаковых последующих выборах игроков результат полной подготовки также совпадает. Сам seed не определяет решения игроков, например стартовую локацию.
- **Seed:** `createGame` принимает только безопасное целое число, включая отрицательные значения. При нарушении проверка отклоняет вызов с ошибкой `Seed must be a safe integer`; проверки числа игроков и уникальности ID сохраняются.
- **Выбор:** `firstPlayerIndex` равен неотрицательному остатку `seed` по `players.length`. `startGame` выбирает `players[firstPlayerIndex].id` и устанавливает этот ID одновременно в `firstPlayerId` и `activePlayerId`. Для трёх игроков seed `0`, `1`, `2`, `3` и `-1` дают индексы `0`, `1`, `2`, `0` и `2` соответственно.
- **Порядок и воспроизводимость:** `players` остаётся порядком мест по часовой стрелке согласно ADR-004; перестановки игроков, `Math.random` и внешнего изменяемого состояния нет. Одинаковые seed и порядок игроков дают одного первого игрока.
- **Граница подготовки:** в `setup` нет `firstPlayerId`. Выбор происходит при `startGame`, который создаёт новый замороженный корневой объект с `phase: regular_play`, `status: in_progress`, `round: 1`, не изменяя входное setup-состояние.
- **Алгоритм полной подготовки (`setup-rng-v1`):** справочные наборы содержат устойчивые уникальные ASCII ID для каждого экземпляра компонента и явный порядок жанров, категорий, клеток и локаций. До случайного отбора каждый набор сортируется по ID в порядке ASCII. Изменение данных меняет `componentsVersion`, изменение правил — `rulesVersion`, изменение алгоритма или порядка операций — `setupAlgorithmVersion`.
- **Поток случайных значений:** для каждого именованного этапа ведётся собственный счётчик, начиная с 0. На очередном шаге вычисляется SHA-256 от UTF-8 строки компактного JSON-массива `["setup-rng-v1", rulesVersion, componentsVersion, seedString, playerIds, stageId, counterString]`. Строки чисел записываются в десятичной форме без ведущих нулей; seed `-0` нормализуется в `"0"`; массив ID игроков сохраняет порядок мест. Сериализация строк соответствует `JSON.stringify`, пробелов между элементами нет. Первые четыре байта хеша читаются как беззнаковое 32-битное число в порядке от старшего байта к младшему; счётчик увеличивается после каждого хеша.
- **Равномерный выбор:** для выбора индекса из `n` элементов, где `1 ≤ n ≤ 2^32`, вычисляется `limit = floor(2^32 / n) * n`; значения `x ≥ limit` пропускаются, иначе индекс равен `x % n`. Пустой набор не допускает выбор. Перемешивание выполняется перестановками: для `i` от `length - 1` до 1 выбрать `j` из `0…i` и обменять элементы `i` и `j`. Пустой набор и набор из одного элемента не потребляют значений. Отбор без возвращения берёт первые нужные элементы перемешанного набора.
- **Порядок подготовки:** (1) сформировать запасы для числа игроков; (2) перемешать заказы, этап `orders`, выложить четыре; (3) перемешать всех художников, этап `artists`, последовательно брать первого для каждой ещё незаполненной пары жанр/категория по `SETUP-004`; (4) перемешать бонусы, этап `artist-bonuses`, раздать закрытым художникам в фиксированном порядке клеток, затем выделить красным художникам коллекционеров; (5) перемешать оставшийся мешочек посетителей, этап `visitors`, и брать посетителей с начала этой последовательности; (6) отдельно перемешать работы каждого жанра, этап `artworks/<genreId>`, в порядке жанров из данных; отложить верхние работы, затем наполнить новые верхние работы посетителями в том же порядке жанров; (7) перемешать репутацию, этап `reputation`, заполнить используемые ячейки рынка сверху вниз по рядам, внутри ряда слева направо, затем локации в порядке данных; (8) перемешать четыре отложенные работы, этап `auction-artworks`, и выбрать число по `SETUP-009`; (9) взять четырёх посетителей на площадь, затем по одному в вестибюли в порядке `players`; (10) определить индекс первого игрока прежней формулой без расхода случайных значений; (11) независимо перемешать колоды целей, этапы `curator-goals` и `dealer-goals`, раздать по одной карте каждого типа в порядке `players`; (12) выполнить записываемые выборы стартовых локаций в обратном порядке хода. Нерандомизированные запасы и планшеты размещаются по соответствующим `SETUP-*`.
- **Восстановление и скрытые данные:** серверный снимок хранит seed, версии, порядок игроков, порядки оставшихся колод/мешочка и выборы подготовки. Для повторного запуска подготовки используются те же входы и версии. До раскрытия целей seed и данные, позволяющие восстановить скрытую раздачу, не входят в публичное представление для других игроков. Контракт случайных операций во время игры определяется отдельно; подготовка не использует `Math.random`, часы или внешнее изменяемое состояние.
- **Граница минимального и полного движка:** действующий `startGame` по-прежнему добавляет `firstPlayerId` только при старте. Полная подготовка вычисляет тот же индекс заранее для обратного порядка выбора локаций, но не начинает обычные ходы до завершения всех выборов. Описанный алгоритм полной подготовки ещё не реализован.
- **Будущие проверки:** совпадение всей случайной раскладки при одинаковых входах; совпадение итогового setup при одинаковых выборах; фиксированные эталонные раскладки для 2/3/4 игроков, включая отрицательный seed; отсутствие дубликатов/потерь компонентов; независимость от порядка входных справочных массивов после сортировки; сохранение результатов при восстановлении; отсутствие скрытых раздач и seed в чужих представлениях.
- **Трассировка:** `createGame` и `startGame` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): параметризованный `выбирает $expectedPlayer при seed: $seed`, `выбирает одного и того же игрока при одинаковом seed`, `проверка невалидных значений в seed` (включает допустимый seed `-1`), `каждый ID игрока достижим подходящим seed`.

### ADR-002 — Представление фаз жизненного цикла

- **Статус:** `approved`.
- **Решение:** `GameState` представляется дискриминируемым объединением шести вариантов по полю `phase`. Существующее поле `status` сохраняется как укрупнённый статус партии и в каждом варианте статически согласуется с фазой.

| `phase` | `status` | `activePlayerId` | Инварианты фазы |
| --- | --- | --- | --- |
| `setup` | `setup` | `null` | Раунд равен 0; подготовка ещё не перешла к обычным ходам. |
| `regular_play` | `in_progress` | ID участника партии | Раунд положительный; определён неизменный первый игрок. |
| `ending_current_round` | `in_progress` | ID участника партии | Сохранён `endTriggeredRound`; оставшиеся игроки заканчивают обычный текущий круг. |
| `final_round` | `in_progress` | ID участника партии | Сохранён `endTriggeredRound`; каждый игрок получает ровно один ход, начиная с первого игрока. |
| `final_scoring` | `in_progress` | `null` | Ходы запрещены; номер раунда сохраняет номер завершённого финального круга. |
| `finished` | `finished` | `null` | Финальный подсчёт завершён; номер последнего завершённого раунда и данные срабатывания конца сохраняются для восстановления и аудита. |

В минимальном движке `startGame` добавляет `firstPlayerId`, принадлежащий `players`, по согласованному seed-контракту ADR-001; в `setup` этого поля нет. Контракт полной случайной подготовки описан в ADR-001; его реализация отсутствует. `endTriggeredRound` существует только в вариантах начиная с `ending_current_round`, поэтому состояние до срабатывания конца не может содержать это поле случайно.

`startGame` допустим только для варианта `setup` и создаёт `regular_play` с раундом 1 и активным первым игроком. `advanceTurn` сохраняет обязательную проверку `status === 'in_progress'`, но дополнительно разрешён только для `regular_play`, `ending_current_round` и `final_round`; вариант `final_scoring` не допускает смену игрока.

Все три фазы с ходами используют один порядок мест `players` по часовой стрелке. Граница круга определяется переходом следующего игрока к `firstPlayerId`. В `ending_current_round` эта граница начинает `final_round` с первого игрока и увеличивает номер раунда. После хода последнего игрока `final_round` не передаёт ход первому повторно, а переходит в `final_scoring` и очищает `activePlayerId`.

Переход в `finished` допустим только после завершения `final_scoring`; безусловный публичный переход из обычной игры в `finished` не предусматривается. Каждая смена фазы должна иметь отдельное доменное событие, а сериализованный снимок должен содержать дискриминант и данные своего варианта. Это позволяет проверять снимок при загрузке и однозначно восстанавливать фазу повтором серверного журнала событий. Формат подсчёта и итоговой таблицы в ADR-002 не определяется.

В [текущем модуле](packages/game-engine/src/index.ts) реализована последовательность `setup` → `regular_play` → `ending_current_round` → `final_round` → `final_scoring`. Завершение запускается явным вызовом `triggerGameEnd`, без оценки игровых индикаторов. `prepareTurn` принимает ход только в `regular_play`, `ending_current_round` и `final_round`, дополнительно проверяя `status: in_progress` при каждом вызове. Тип `FinishedGameState` существует, но переход в `finished` и сам финальный подсчёт не реализованы. Доменные события, проверка загружаемых снимков и восстановление по журналу также остаются требованиями, а не готовыми возможностями.

### ADR-003 — Команды и черновик составного хода

- **Статус:** `approved`.
- **Граница состояния:** `TurnDraft` является отдельным неизменяемым значением и не входит в `GameState`. Формирование и подтверждение черновика не меняют состояние партии; игровые эффекты возникают только при применении подтверждённой команды.
- **Формат черновика:** минимальные поля — `playerId`, необязательные до подтверждения `movement` и `locationAction`, а также не более одного `management`. Выбор управления хранит `timing: 'before_location' | 'after_location'` и саму команду управления.
- **Формат подтверждённой команды:** `ConfirmedTurnCommand` содержит `type: 'perform_turn'`, `playerId`, обязательные `movement` и `locationAction` и необязательный `management`. Перемещение всегда выполняется первым; `timing` определяет взаимный порядок управления и действия локации.
- **Подготовленный план:** `PreparedTurn` — техническое дополнение API для подготовки подтверждённой команды к будущему исполнению. Его `steps` имеет тип `TurnExecutionSteps`: без управления это `[movement, locationAction]`, с `before_location` — `[movement, management.command, locationAction]`, с `after_location` — `[movement, locationAction, management.command]`. План содержит команды, а не доменные события.
- **Редактирование:** публичный `TurnDraftEdit` является дискриминируемым объединением операций `set_movement`, `set_location_action`, `set_management_action` и `clear_management_action`. Повторная установка заменяет соответствующее единственное поле и не накапливает действия.
- **Публичные функции:** `createTurnDraft(playerId)` создаёт пустой черновик; `updateTurnDraft(draft, edit)` возвращает новый черновик; `confirmTurnDraft(draft)` возвращает `ConfirmedTurnCommand`; `prepareTurn(state, command)` возвращает `PreparedTurn`. Будущий `applyTurn(state, command)` должен возвращать новый `GameState`.
- **Проверка и применение:** `confirmTurnDraft` отклоняет черновик без перемещения или действия локации. Единственное поле `management` структурно запрещает два действия управления. `prepareTurn` при каждом вызове проверяет актуальные фазу, статус, принадлежность активного игрока партии, совпадение `command.playerId` с ним и наличие обязательных частей, затем возвращает новый независимый замороженный план. Эта функция не проверяет игровые предусловия конкретных действий, не резервирует и не применяет ход. Будущий `applyTurn` обязан заново проверить актуальное состояние и все зависящие от него предусловия, применить части в согласованном порядке как одну атомарную операцию и при отклонении не менять входной снимок.
- **Выдворение:** возможности выдворения не входят в `TurnDraft` или `ConfirmedTurnCommand`. В будущем они фиксируются в состоянии после применения обычного хода и разрешаются отдельными командами до `advanceTurn`; точный формат этих команд и ожидающих возможностей определяется при реализации `EJECT-*`.
- **Граница контракта:** `MovementCommand`, `LocationActionCommand` и `ManagementActionCommand` здесь обозначают категории команд. Их конкретные дискриминированные варианты, игровые данные и доменные события этим ADR не утверждаются.
- **Тестирование:** отдельно проверяются неизменяемое редактирование черновика, его структурное подтверждение, state-зависимая подготовка, три точных порядка команд, независимость и заморозка плана, повторная проверка после смены активного игрока, а в будущем — атомарность применения и отсутствие изменения исходного состояния при ошибке.
- **Текущее состояние:** в [модуле движка](packages/game-engine/src/index.ts) реализованы категорийные маркеры команд, `TurnDraft`, `TurnDraftEdit`, `ConfirmedTurnCommand`, `PreparedTurn`, `TurnExecutionSteps`, создание, неизменяемое редактирование, структурное подтверждение черновика и подготовка плана по актуальному снимку. [Тесты](packages/game-engine/src/index.test.ts) проверяют три порядка, все разрешённые и запрещённые фазы, статус, активного и командующего игроков, обязательные части на JS-границе, сохранность входов, независимую заморозку результата, повторные вызовы, повторную проверку после `advanceTurn` и полный путь от черновика до плана. `applyTurn`, игровые эффекты, полная проверка игровых предусловий и доменные события отсутствуют; существующий `advanceTurn` выполняет только ротацию активного игрока и не считается применением составного хода.

## 4. Общие инварианты

### CORE-001 — Число участников MVP

- **Источник / фаза / триггер:** границы продукта и подготовка, с. 2; создание партии.
- **Условия:** обычная онлайн-партия содержит 2, 3 или 4 места.
- **Эффект:** конфигурация и список игроков содержат одинаковое допустимое число участников.
- **Исключения:** официальный одиночный вариант не является партией с одним обычным местом.
- **События:** `GameCreated` после успешной полной подготовки.
- **Проверки:** принять 2/3/4 места; отклонить другое число и несовпадение конфигурации со списком.
- **Статус:** `spec: approved` · `implementation: yes` · `tests: yes`.
- **Трассировка:** runtime-проверка допустимых значений и совпадения со списком игроков в `createGame` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): параметризованные `отклоняет согласованную конфигурацию на $playerCount игроков`, `принимает допустимую конфигурацию на %i игроков` и `rejects a player count that differs from the configuration`.

### CORE-002 — Ограниченность компонентов

- **Источник / фаза / триггер:** подготовка, с. 2; любая попытка получить компонент.
- **Условия:** монеты не ограничены; остальные физические компоненты ограничены текущим запасом.
- **Эффект:** доступный компонент перемещается из соответствующего запаса.
- **Исключения:** если компонент закончился, игрок его не получает; специальные правила билетов описаны в `TICKET-002`.
- **События:** событие получения создаётся только для фактически полученного количества.
- **Проверки:** получение из непустого запаса; пустой запас не создаёт компонент и не уводит количество ниже нуля.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### CORE-003 — Цель и победитель

- **Источник / фаза / триггер:** обзор, с. 4; завершение финального подсчёта.
- **Условия:** все этапы финального подсчёта выполнены.
- **Эффект:** победителем становится участник с наибольшим итоговым количеством монет; ничьи разрешаются по `SCORE-007`.
- **Исключения:** победителей может быть несколько, если все критерии ничьей равны.
- **События:** `WinnerDetermined`.
- **Проверки:** единственный лидер; полная ничья после всех дополнительных критериев.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — чистая функция определения победителей реализована; интеграция с финальным подсчётом, событие `WinnerDetermined` и переход в `finished` отсутствуют.
- **Трассировка:** `determineWinners` в [модуле определения победителей](packages/game-engine/src/winner-determination.ts); [тесты](packages/game-engine/test/winner-determination.test.ts): `expect soleLeaderCoins`, `expect allWin`.

### CORE-004 — Неизменяемые переходы движка

- **Источник / фаза / триггер:** технический принцип проекта; любой переход состояния.
- **Условия:** движок получает снимок `GameState`.
- **Эффект:** успешный переход возвращает новый неизменяемый корневой объект, а отклонённый вызов не меняет входной снимок.
- **Исключения:** ссылки на неизменённые вложенные данные могут сохраняться, если контракт перехода это разрешает.
- **События:** отсутствуют при отклонении.
- **Проверки:** сравнить вход с глубокой копией после успешного и отклонённого вызова; проверить заморозку результата.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — последовательное разрешение ничьей реализовано как чистая функция; вычисление входных итогов из `GameState` и событие `WinnerDetermined` отсутствуют.
- **Трассировка:** `determineWinners` в [модуле определения победителей](packages/game-engine/src/winner-determination.ts); [тесты](packages/game-engine/test/winner-determination.test.ts): победа по каждому критерию, полная ничья, сохранение порядка и отклонение игрока с меньшим числом монет независимо от поздних критериев.
- **Трассировка:** неизменяемость `prepareTurn` проверена сценариями `returns a new frozen plan independent from mutable inputs`, всеми параметризованными сценариями отклонения и `returns equal but independent plans for repeated preparation` в [тестах движка](packages/game-engine/src/index.test.ts). Статус остаётся `partial`, пока не реализованы остальные переходы и применение игровых эффектов.

## 5. Подготовка обычной партии

### SETUP-001 — Пулы посетителей и билетов

- **Источник / фаза / триггер:** подготовка, с. 2; создание партии.
- **Условия:** известное число игроков.
- **Эффект:** при 4 игроках используются 14 инвесторов, 14 знаменитостей, 12 коллекционеров и по 20 билетов каждого цвета; при 3 — 12 инвесторов, 12 знаменитостей, 10 коллекционеров и по 15 билетов; при 2 — 10 инвесторов, 10 знаменитостей, 8 коллекционеров и по 10 билетов. Это полный доступный пул до размещения посетителей на художниках, произведениях, площади и вестибюлях; удаляются соответственно по 0/2/4 посетителя каждого типа относительно комплекта на четверых.
- **Исключения:** удалённые компоненты недоступны до конца партии.
- **События:** `VisitorBagPrepared`, `TicketOfficePrepared`.
- **Проверки:** точные количества для 2/3/4 игроков; отсутствие удалённых компонентов в доступном запасе.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### SETUP-002 — Начальные влияние и монеты

- **Источник / фаза / триггер:** подготовка, с. 2–3; создание партии.
- **Условия:** места 2–4 игроков переданы в `createGame` как конфигурации с `id`, `name` и `kind`.
- **Эффект:** движок создаёт для каждого места отдельный `PlayerState`, сохраняет `id`, `name`, `kind` и исходный порядок мест и назначает ровно 10 монет и 10 влияния. Значения одинаковы для людей и ботов, не зависят от числа игроков или seed, включая отрицательный, и не назначаются вызывающей стороной.
- **Исключения:** дополнительные входные поля, структурно совместимые с ресурсами игрока, не переопределяют стартовые значения и не требуют отдельной ошибки: `createGame` всё равно назначает 10 монет и 10 влияния.
- **События:** начальные значения должны входить в `GameCreated`; доменное событие ещё не реализовано.
- **Проверки:** стартовые значения для 2/3/4 игроков и обоих `kind`; независимость от seed; игнорирование входных нестартовых значений; сохранение данных, порядка и неизменности входа; заморозка корня, `config`, массива и объектов игроков; сохранение произвольных текущих ресурсов через `startGame`, `advanceTurn`, `triggerGameEnd` и переходы до `final_scoring` без переинициализации.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — модель ресурсов и поведение `createGame` реализованы и протестированы, но `GameCreated` отсутствует.
- **Трассировка:** `PlayerConfig`, `PlayerState` и `createGame` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): `выбирает количество игроков, сохраняет их данные, порядок, проверяет ресурсы и неизменность входа`, `влияние и монеты не изменяются с раундами`.

### SETUP-003 — Заказы

- **Источник / фаза / триггер:** подготовка, с. 2; создание партии.
- **Условия:** доступен полный набор карт заказов.
- **Эффект:** колода перемешивается seed-детерминированно; четыре верхние карты образуют открытую область заказов.
- **Исключения:** нет.
- **События:** `OrderMarketPrepared`.
- **Проверки:** одинаковый seed даёт одинаковый порядок; область содержит четыре карты, исключённые из закрытой колоды.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### SETUP-004 — Выбор художников

- **Источник / фаза / триггер:** подготовка, с. 2; создание партии.
- **Условия:** 16 художников распределены по четырём жанрам и двум категориям.
- **Эффект:** seed-детерминированный отбор заполняет восемь уникальных клеток так, чтобы каждый жанр был представлен одним художником каждой категории; первый выбранный художник синей категории открыт и получает начальную известность, остальные закрыты.
- **Исключения:** художник, чья клетка уже занята, исключается из текущей партии.
- **События:** `ArtistsPrepared`, `ArtistOpened` для начального художника.
- **Проверки:** восемь уникальных клеток и требуемое распределение; одинаковый seed воспроизводит выбор.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### SETUP-005 — Бонусы, коллекционеры и подписи художников

- **Источник / фаза / триггер:** подготовка, с. 2; после `SETUP-004`.
- **Условия:** художники выбраны; бонусы распределяются при подготовке так, чтобы у каждого закрытого художника был ровно один бонус. Отсутствие бонуса у закрытого художника является некорректным состоянием подготовки.
- **Эффект:** на каждого закрытого художника кладётся случайный бонус; на каждого красного художника — один коллекционер из мешочка; рядом с каждым художником размещаются два его жетона подписи.
- **Исключения:** начальный открытый художник бонус не получает; неиспользованные бонусы удаляются из партии.
- **События:** входят в `ArtistsPrepared`.
- **Проверки:** бонус отсутствует только у начального открытого художника; количество подписей каждого художника равно двум.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### SETUP-006 — Стопки произведений и посетители на рынке

- **Источник / фаза / триггер:** подготовка, с. 2; создание партии.
- **Условия:** известны четыре жанра произведений.
- **Эффект:** стопка каждого жанра перемешивается отдельно; верхняя работа временно откладывается; на новую верхнюю работу помещаются случайно выбранные посетители в количестве, равном напечатанному числу билетов независимо от их цветов. Количество фиксировано свойствами работы; случайным является состав посетителей.
- **Исключения:** отложенные работы далее используются для выдающихся произведений по `SETUP-009`.
- **События:** `ArtworkMarketPrepared`.
- **Проверки:** четыре независимые стопки; число посетителей на каждой верхней работе совпадает с её значением.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### SETUP-007 — Реклама

- **Источник / фаза / триггер:** подготовка, с. 2; создание партии.
- **Условия:** доступны жетоны рекламы всех уровней.
- **Эффект:** для каждого уровня рекламы 1–5 используются ровно 4 жетона, всего 20; жетоны группируются на предназначенных для уровней клетках.
- **Исключения:** количество жетонов ограничено.
- **События:** `PromotionSupplyPrepared`.
- **Проверки:** каждый жетон находится в стопке своего уровня; общий запас сохраняется.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### SETUP-008 — Международный рынок

- **Источник / фаза / триггер:** подготовка, с. 2–3; создание партии.
- **Условия:** доступен пул жетонов репутации.
- **Эффект:** при 3–4 игроках 12 случайных жетонов заполняют верхние четыре ряда трёх колонок; при 2 игроках восемь жетонов заполняют только первую и третью колонки. Дополнительно по одному из четырёх случайных жетонов размещается у каждой локации.
- **Исключения:** средняя колонка в партии на двоих не используется; остальные жетоны не участвуют в этих ячейках.
- **События:** `InternationalMarketPrepared`, `LocationReputationPrepared`.
- **Проверки:** раскладки для 2/3/4 игроков; уникальность выбранных жетонов; средняя колонка пуста при двух игроках.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### SETUP-009 — Выдающиеся произведения

- **Источник / фаза / триггер:** подготовка, с. 3; после `SETUP-006`.
- **Условия:** отложено по одной работе каждого жанра.
- **Эффект:** отложенные работы перемешиваются; на мольберты помещаются 3 работы при 4 игроках, 2 при 3 игроках и 1 при 2 игроках.
- **Исключения:** неиспользованные работы и мольберты удаляются из партии.
- **События:** `MasterpieceAuctionPrepared`.
- **Проверки:** количество соответствует числу игроков; выставленные работы уникальны и выбраны из четырёх отложенных.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no` — последовательность отбора и количество работ подтверждены.

### SETUP-010 — Начальные посетители поля

- **Источник / фаза / триггер:** подготовка, с. 3; создание партии.
- **Условия:** мешочек подготовлен.
- **Эффект:** четыре случайных посетителя помещаются на площадь и по одному случайному посетителю — в вестибюль каждого участника.
- **Исключения:** выбранные посетители удаляются из мешочка.
- **События:** `InitialVisitorsPlaced`.
- **Проверки:** площадь содержит четыре, каждый вестибюль один; суммарное число посетителей сохраняется.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### SETUP-011 — Первый игрок и круговой порядок

- **Источник / фаза / триггер:** подготовка, с. 3; создание партии.
- **Условия:** участники размещены в круговом порядке.
- **Эффект:** в полной подготовке первый игрок выбирается случайно и воспроизводимо через seed; обычная партия начинается с его хода и продолжается по часовой стрелке. Для минимального движка согласован узкий выбор по неотрицательному остатку seed, описанный в ADR-001.
- **Исключения:** порядок мест зафиксирован в `players` согласно ADR-004; контракт всей случайной подготовки согласован в ADR-001, но ещё не реализован.
- **События:** `FirstPlayerSelected`.
- **Проверки:** одинаковый seed и порядок игроков дают одинакового первого игрока; каждый допустимый ID может быть выбран набором seed; проверяются положительные, нулевой и отрицательный seed, совпадение первого и активного игроков и отклонение небезопасного или нецелого seed.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — seed-выбор и круговой порядок реализованы; согласованная полная подготовка и событие `FirstPlayerSelected` отсутствуют.
- **Трассировка:** `createGame` и `startGame` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): `выбирает $expectedPlayer при seed: $seed`, `выбирает одного и того же игрока при одинаковом seed`, `проверка невалидных значений в seed`, `каждый ID игрока достижим подходящим seed`.

### SETUP-012 — Планшет и стартовая локация игрока

- **Источник / фаза / триггер:** подготовка, с. 3; после выбора первого игрока.
- **Условия:** для каждого игрока доступны 10 помощников, планшет, галерист и карты целей.
- **Эффект:** восемь помощников заполняют очередь безработных, два занимают любые рабочие места офиса. До выбора стартовых локаций каждый игрок получает ровно по одной случайной карте куратора и арт-дилера без выбора из нескольких карт. Затем в обратном порядке хода игроки выбирают только ещё не занятые стартовые локации, размещают там галериста и забирают жетон репутации выбранной локации на третью перегородку.
- **Исключения:** оставшиеся у локаций жетоны репутации удаляются после выбора всех игроков. Карты целей доступны владельцу до его выбора локации и скрыты от остальных игроков до финального подсчёта; сервер хранит полный набор данных, а представление для каждого игрока исключает чужие цели и скрытые колоды.
- **События:** `PlayerBoardPrepared`, `StartingLocationChosen`, `PrivateGoalsDealt`.
- **Проверки:** обратный порядок выбора; запрет занятой локации; по 10 помощников, две занятые офисные клетки; ровно одна случайная карта каждого типа без выбора; владелец видит цели до выбора локации, соперники — только при финальном подсчёте.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no` — согласованные подготовка и скрытые цели; данные помощников, клеток и 8 карт целей перенесены в раздел 17.

## 6. Раунды, ход и передача инициативы

### TURN-001 — Начало обычной партии

- **Источник / фаза / триггер:** процесс игры, с. 5; завершение подготовки.
- **Условия:** подготовка полностью завершена и первый игрок определён.
- **Эффект:** начинается первый раунд, активным становится первый игрок.
- **Исключения:** запуск неполной или уже начатой партии запрещён.
- **События:** `GameStarted`, `RoundStarted`, `TurnStarted`.
- **Проверки:** корректное начало; отклонение повторного запуска без изменения состояния.
- **Статус:** `spec: draft` · `implementation: partial` · `tests: partial` — `startGame` запускает минимальное setup-состояние с seed-выбором первого игрока, раундом 1 и совпадающими первым и активным игроками; повторный запуск запрещён. Полная подготовка, проверка её завершённости и доменные события ещё отсутствуют.
- **Трассировка:** `startGame` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): `startGame phase:regular_play`, `startGame is const? no mutation`, `createGame is frozen` (отклонение повторного запуска), `выбирает $expectedPlayer при seed: $seed`.

### TURN-002 — Состав обычного хода

- **Источник / фаза / триггер:** процесс игры и действия управления, с. 5; начало хода.
- **Условия:** ход принадлежит активному игроку.
- **Эффект:** игрок обязательно перемещает галериста и выполняет одно действие новой локации; дополнительно он может выполнить не более одного действия управления до либо после действия локации.
- **Исключения:** действие управления необязательно; порядок фиксируется выбранной последовательностью действий.
- **События:** подтверждение черновика само по себе не создаёт игровых эффектов или доменных событий по ADR-003. При успешном атомарном применении хода создаётся упорядоченный набор событий выполненных действий; отклонённый ход не создаёт событий.
- **Проверки:** варианты управление→локация, локация→управление и только локация; отклонить два действия управления или отсутствие действия локации.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — по ADR-003 в [модуле движка](packages/game-engine/src/index.ts) реализованы создание, неизменяемое редактирование и структурное подтверждение черновика, а также `prepareTurn`: проверка фазы и активного игрока и построение независимого замороженного плана в трёх допустимых порядках. В [тестах](packages/game-engine/src/index.test.ts) проверены операции с черновиком, три порядка плана, разрешённые и запрещённые фазы, принадлежность хода, обязательные части, неизменяемость, повторная подготовка, повторная проверка после `advanceTurn` и сквозной сценарий. `applyTurn`, игровые предусловия и эффекты, доменные события и атомарность применения ещё отсутствуют.

### TURN-003 — Перемещение галериста

- **Источник / фаза / триггер:** действия локаций, с. 5; обязательное перемещение хода.
- **Условия:** если галерист находится в локации, он обязан перейти в другую локацию; если находится дома в галерее, может выбрать любую локацию.
- **Эффект:** галерист занимает выбранную локацию и открывает одно из двух её действий.
- **Исключения:** остаться в прежней локации нельзя.
- **События:** `GalleristMoved`.
- **Проверки:** переход между разными локациями; отклонение прежней локации; выход из домашней галереи в любую локацию.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### TURN-004 — Оставление помощника

- **Источник / фаза / триггер:** действия локаций, с. 5; перемещение между двумя локациями.
- **Условия:** у игрока есть помощник в офисе или другой локации.
- **Эффект:** перед уходом игрок может оставить ровно одного своего помощника в покидаемой локации, переместив его из допустимого источника.
- **Исключения:** при отсутствии доступного помощника эффект недоступен; помощник не обязателен.
- **События:** `AssistantLeftAtLocation`.
- **Проверки:** помощник из офиса и другой локации; отсутствие помощника; попытка оставить больше одного.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### TURN-005 — Разрешение последствий и следующий игрок

- **Источник / фаза / триггер:** процесс игры, с. 5–6; окончание действий активного игрока.
- **Условия:** действие локации и выбранное действие управления завершены.
- **Эффект:** опустошение первой цветной стопки билетов только назначает промежуточный подсчёт и не начисляет доход немедленно. После действий активного игрока разрешается получение стартовой репутации, затем дополнительные действия выдворения и возникшие при них отложенные эффекты. После этого выполняется назначенный промежуточный подсчёт по составу галерей на момент начисления, и лишь затем ход переходит следующему участнику по кругу. Выдворенный игрок не получает новый обычный ход. Если первая стопка билетов опустела в действии выдворения, подсчёт проводится в конце этого же обычного хода до передачи инициативы.
- **Исключения:** в дополнительном финальном раунде действия выдворения подавлены по `END-004`.
- **События:** события получения стартовой репутации, действий выдворения и остальных отложенных эффектов, затем события назначенного промежуточного подсчёта; после их завершения `TurnEnded` и передача инициативы с `TurnStarted` либо переходом фазы по END-005.
- **Проверки:** выдворение не меняет круговой порядок; передача хода происходит после всех отложенных эффектов.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — круговой порядок и начисление промежуточного дохода после действий выдворения согласованы; текущий `advanceTurn` реализует только ротацию, без игровых эффектов и подсчёта.
- **Трассировка:** `advanceTurn` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): `3 players ,next round, activePlayerId first player`, `4 players ,next round, activePlayerId first player`, `переходы хода и увеличение раунда при первом игроке, отличном от players[0]`. Эти сценарии не проверяют составной ход, выдворение и отложенные эффекты.

### TURN-006 — Граница раунда

- **Источник / фаза / триггер:** процесс и конец игры, с. 5; передача хода первому игроку.
- **Условия:** завершён ход игрока, стоящего непосредственно перед первым игроком в круговом порядке.
- **Эффект:** текущий раунд заканчивается, номер раунда увеличивается и начинается ход первого игрока.
- **Исключения:** согласно ADR-002, в `ending_current_round` эта граница начинает `final_round`; в `final_round` она переводит партию в `final_scoring` без увеличения номера раунда и без повторной передачи хода первому игроку.
- **События:** `RoundEnded`, `RoundStarted`.
- **Проверки:** полный круг для 2/3/4 игроков; неполный круг не увеличивает номер; при первом игроке, отличном от `players[0]`, номер увеличивается только при возврате к `firstPlayerId`.
- **Статус:** `spec: draft` · `implementation: partial` · `tests: partial` — граница по `firstPlayerId` и переходы фаз реализованы и проверены; доменные события ещё отсутствуют.
- **Трассировка:** `advanceTurn` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): `next round, activePlayerId first player`, `3 players ,next round, activePlayerId first player`, `4 players ,next round, activePlayerId first player`, `переходы хода и увеличение раунда при первом игроке, отличном от players[0]`, `final_scoring, all round`.

## 7. Условия окончания партии

### END-001 — Три индикатора окончания

- **Источник / фаза / триггер:** конец игры, с. 5; после любого атомарного эффекта, меняющего кассу билетов, статус художника или мешочек посетителей.
- **Условия:** отслеживаются: касса полностью без билетов; не менее двух суперзвёзд; мешочек посетителей пуст.
- **Эффект:** состояние хранит, какие индикаторы уже выполнены.
- **Исключения:** пустая отдельная стопка билетов запускает промежуточный подсчёт, но не равна пустой кассе.
- **События:** `EndConditionReached` для впервые выполненного индикатора.
- **Проверки:** каждый индикатор отдельно; различить пустой цвет билетов и полностью пустую кассу.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### END-002 — Запуск завершения

- **Источник / фаза / триггер:** конец игры, с. 5; выполнены минимум два индикатора `END-001`.
- **Условия:** партия находится в обычной фазе.
- **Эффект:** фаза один раз переходит из `regular_play` в `ending_current_round`; номер текущего раунда сохраняется в `endTriggeredRound`, первый и активный игроки не меняются.
- **Исключения:** выполнение третьего индикатора не создаёт повторный переход.
- **События:** `GameEndTriggered`.
- **Проверки:** один индикатор не запускает конец; любая пара запускает; повторная оценка идемпотентна.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — явный вызов `triggerGameEnd` выполняет неизменяемый переход только из `regular_play`. Повторный вызов отклоняется с ошибкой `Only regular_play`, не меняя состояние. Автоматическая проверка двух индикаторов, идемпотентная повторная оценка условий и событие `GameEndTriggered` ещё не реализованы.
- **Трассировка:** `triggerGameEnd` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): `triggerGameEnd creates a frozen new state without mutating input`, `triggerGameEnd, is regular_play`, `triggerGameEnd rejects a repeated call`. Это проверки перехода и его ограничений, а не игровых индикаторов.

### END-003 — Доигрывание текущего раунда

- **Источник / фаза / триггер:** конец игры, с. 5; вход в `ending_current_round`.
- **Условия:** условие конца могло сработать в ход любого игрока.
- **Эффект:** оставшиеся участники текущего раунда получают обычные ходы до его естественной границы.
- **Исключения:** уже завершившие ход в этом раунде не ходят повторно.
- **События:** обычные события хода; на границе `FinalRoundStarted`.
- **Проверки:** триггер в ход первого, среднего и последнего игрока.
- **Статус:** `spec: draft` · `implementation: partial` · `tests: partial` — `advanceTurn` сохраняет круговой порядок в `ending_current_round`, а при возврате к `firstPlayerId` начинает `final_round` и увеличивает номер раунда. Проверены переходы с разным положением активного игрока относительно первого; игровые действия, отложенные эффекты и события отсутствуют.
- **Трассировка:** `advanceTurn` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): `final_scoring, all round`, `final_scoring, all round firstPlayerId: player-2 activePlayerId: player-1`, `final_scoring, all round firstPlayerId: player-2 activePlayerId: player-3` ([сценарий с переходами](packages/game-engine/src/index.test.ts#L798)). Последнее имя также есть у отдельного теста отклонения `triggerGameEnd` из `setup`; здесь указан сценарий с вызовами `advanceTurn`.

### END-004 — Дополнительный финальный раунд

- **Источник / фаза / триггер:** конец игры, с. 5; завершение раунда из `END-003`.
- **Условия:** начинает первый игрок.
- **Эффект:** каждый участник ровно один раз выполняет обычный ход в круговом порядке.
- **Исключения:** выдворенная фишка возвращается домой, но её владелец не выполняет действие выдворения.
- **События:** `FinalRoundStarted`, обычные события ходов, `FinalRoundEnded`.
- **Проверки:** по одному ходу на игрока; подавление действия выдворения при сохранении возврата фишки.
- **Статус:** `spec: draft` · `implementation: partial` · `tests: partial` — реализован один финальный круг от `firstPlayerId` до перехода в `final_scoring`. Это ротация состояний: составной ход, выдворение, возврат фишек и доменные события ещё не реализованы.
- **Трассировка:** `advanceTurn` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): `final_scoring, all round`, `final_scoring, all round firstPlayerId: player-2 activePlayerId: player-1`, `final_round advanceTurn`.

### END-005 — Переход к подсчёту

- **Источник / фаза / триггер:** конец игры, с. 5; окончание дополнительного финального раунда.
- **Условия:** все отложенные эффекты последнего хода разрешены.
- **Эффект:** активный игрок очищается, партия переходит в фазу подсчёта; после `SCORE-001`–`SCORE-007` становится завершённой.
- **Исключения:** публичный безусловный переход из обычной игры сразу в `finished` запрещён.
- **События:** `FinalScoringStarted`, позднее `GameFinished`.
- **Проверки:** нельзя завершить обычную фазу вручную; корректная последовательность фаз сохраняет исходное состояние неизменным.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — реализован переход `final_round` → `final_scoring`: `activePlayerId` очищается, `round`, `firstPlayerId` и `endTriggeredRound` сохраняются; дальнейший `advanceTurn` запрещён. Отложенные эффекты, события, `SCORE-001`–`SCORE-007` и переход `final_scoring` → `finished` отсутствуют. `FinishedGameState` пока только описывает тип завершённого состояния.
- **Трассировка:** `advanceTurn` и `FinishedGameState` в [модуле движка](packages/game-engine/src/index.ts); [тесты](packages/game-engine/src/index.test.ts): `final_scoring, all round`, `final_scoring, all round firstPlayerId: player-2 activePlayerId: player-1`, `final_round advanceTurn`, `phase: final_scoring error`. Тест `finish game` проверяет запрет повторного запуска готовой фикстуры `finished`, а не выполнение подсчёта или переход в эту фазу.

## 8. Действия управления

### MGMT-001 — Выбор и момент действия управления

- **Источник / фаза / триггер:** действия управления, с. 5; собственный обычный ход или разрешённое выдворение.
- **Условия:** в обычный ход доступно не более одного действия управления до или после локации; при выдворении оно является одной из альтернатив.
- **Эффект:** выполняется перемещение посетителей либо получение награды заказа.
- **Исключения:** игрок может отказаться.
- **События:** `ManagementActionStarted` и событие выбранного действия.
- **Проверки:** оба момента обычного хода; отказ; недопустимое второе действие.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### MGMT-002 — Перемещение посетителей билетами

- **Источник / фаза / триггер:** действия управления, с. 5; выбор перемещения посетителей.
- **Условия:** каждый сброшенный билет соответствует типу перемещаемого посетителя.
- **Эффект:** за билет посетитель движется на один шаг к галерее игрока: площадь→свой вестибюль, свой вестибюль→своя галерея либо чужой вестибюль→площадь. Одного посетителя можно переместить несколько раз за одно действие.
- **Исключения:** движение в обратную сторону и перемещение из любой галереи билетами запрещены; сброшенные билеты не возвращаются в кассу.
- **События:** `TicketSpent`, `VisitorMoved` для каждого шага.
- **Проверки:** допустимые маршруты; два шага одного посетителя; отклонение обратного маршрута и чужой галереи.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### MGMT-003 — Лимит коллекционеров

- **Источник / фаза / триггер:** действия управления, с. 5; попытка поместить коллекционера в галерею.
- **Условия:** вместимость коллекционеров равна `1 + число проданных игроком произведений`.
- **Эффект:** коллекционер входит в галерею только при наличии свободного места.
- **Исключения:** правило применяется ко всем эффектам перемещения, если конкретный эффект явно не отменяет лимит.
- **События:** обычное `VisitorMoved`.
- **Проверки:** вместимость 1 до первой продажи; рост после продажи; отклонение сверх лимита.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### MGMT-004 — Награда карты заказа

- **Источник / фаза / триггер:** действия управления, с. 5; выбор доступной стороны карты заказа.
- **Условия:** на активной стороне карты ещё нет помощника; у игрока есть помощник в офисе или локации. При собственном действии выдворения игрок также может использовать именно своего помощника, выдворенного другим игроком, с клетки выдворения, даже если других доступных помощников нет.
- **Эффект:** помощник помещается на карту, награда её текущей стороны применяется ровно один раз. У всех карт заказов одинаковая оборотная сторона по `ORDER-BACK-001`: выбранная денежная награда даёт 2 монеты за каждого инвестора и 1 монету за каждого коллекционера в своей галерее; выбранная награда влияния даёт 2 влияния за каждую знаменитость и 1 влияние за каждого коллекционера в своей галерее. Состав галереи учитывается при выполнении действия управления, а не при продаже.
- **Исключения:** помощник остаётся на карте до продажи, замены выполненного заказа или иного указанного возврата.
- **События:** `AssistantAssignedToOrder`, события конкретной награды.
- **Проверки:** первая награда; повторное получение запрещено; обратная сторона после продажи может быть активирована отдельно.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no` — все 20 лицевых наград и общий оборот перенесены в 17.5; полное правило остаётся черновым.

## 9. Выдворение и возвращение домой

### EJECT-001 — Выдворение чужой фишки

- **Источник / фаза / триггер:** действия выдворения, с. 6; галерист входит в занятую чужой фишкой локацию.
- **Условия:** целевая фишка — чужой галерист или помощник.
- **Эффект:** фишка переносится на клетку выдворения той же локации; после полного хода активного игрока её владелец получает возможность действия выдворения.
- **Исключения:** следующий обычный ход всё равно принадлежит следующему игроку по кругу.
- **События:** `PieceEjected`, позднее `EjectionOpportunityGranted`.
- **Проверки:** чужой галерист и помощник; возможность появляется только после активного хода.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### EJECT-002 — Собственный помощник

- **Источник / фаза / триггер:** действия выдворения, с. 6; игрок входит в локацию со своим помощником.
- **Условия:** выдворяется собственная фишка помощника.
- **Эффект:** при наличии свободного рабочего места помощник возвращается в офис; если все четыре места заняты, возвращающийся помощник навсегда удаляется из партии, не попадает в очередь безработных и не может быть нанят повторно.
- **Исключения:** владелец не получает действие выдворения.
- **События:** `OwnAssistantEjected`, затем `AssistantReturnedHome` или `AssistantRemovedFromGame`.
- **Проверки:** возврат без дополнительного действия; полный офис приводит к удалению возвращающегося помощника.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### EJECT-003 — Альтернативы действия выдворения

- **Источник / фаза / триггер:** действия выдворения, с. 6; предоставлена возможность.
- **Условия:** игрок выбирает не более одной альтернативы.
- **Эффект:** игрок получает не новый обычный ход, а специальное дополнительное действие: либо тратит влияние до предыдущего символа известности и выполняет действие текущей локации, либо выполняет одно действие управления, либо отказывается.

### ARTWORK-005 — Размещение работы и подписи

- **Источник / фаза / триггер:** покупка, с. 8; после наград.
- **Условия:** доступна перегородка.
- **Эффект:** работа переворачивается и занимает крайнюю левую свободную перегородку. Исключение для третьей выставленной работы: если она является шедевром, она занимает свободную четвёртую перегородку; если четвёртая уже занята другим шедевром, занимает третью. Соответствующая подпись перемещается к делению текущего звёздного рейтинга и определяет текущую цену продажи, которая далее может измениться по `FAME-001`.
- **Исключения:** при контракте используется подпись с клетки контракта. Работа, приобретаемая по контракту у уже состоявшейся суперзвезды, сразу размещается как шедевр; наличие такого шедевра учитывается при определении вместимости по `ARTWORK-002`. Если художник стал суперзвездой в процессе текущей покупки, сама покупаемая работа также сразу размещается как шедевр, независимо от того, была покупка обычной или контрактной.
- **События:** `ArtworkExhibited`, `SignaturePriceSet`.
- **Проверки:** первая и последующая свободная перегородка; третья работа — обычная либо шедевр; свободная четвёртая перегородка и четвёртая, занятая другим шедевром; контракт очищается; цена соответствует рейтингу после увеличения известности.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.
- **Граница согласования:** согласованное уточнение взаимодействия зафиксировано в REVIEW-001 (17.11); ранее согласованные части правила сохраняются.


### ARTWORK-006 — Обновление рынка и стартовая репутация

- **Источник / фаза / триггер:** покупка, с. 8; работа снята с вершины стопки.
- **Условия:** купленная работа снята с вершины стопки. Получение стартовой репутации проверяется независимо от наличия следующей работы в стопке.
- **Эффект:** если в стопке есть следующая работа, на неё помещаются случайные посетители по числу напечатанных билетов, насколько позволяет мешочек. Когда в галерее появляется третья выставленная работа, стартовый жетон репутации с третьей перегородки переносится на эту работу, в том числе если шедевр размещён на четвёртой перегородке по `ARTWORK-005`. Жетон остаётся на работе до конца хода, затем переносится на свободную клетку репутации игрока и приносит награду этой клетки. После получения жетона игрок обязан вернуть одного выбранного посетителя из своего вестибюля на площадь, если посетители есть.
- **Исключения:** если в момент получения свободной клетки репутации нет, стартовый жетон теряется и удаляется из партии. Пустой вестибюль не препятствует получению жетона и награды клетки; перемещение посетителя пропускается. Не активированный к финальному подсчёту стартовый жетон удаляется. Один стартовый жетон не может быть получен повторно.
- **События:** `ArtworkMarketRefilled`, возможные `ReputationTokenClaimed`, `BoardRewardClaimed`, `VisitorMoved`.
- **Проверки:** полный/частично пустой мешочек; последняя работа в стопке не блокирует стартовую репутацию; появление третьей обычной работы и третьего произведения-шедевра на четвёртой перегородке; перенос жетона сначала на работу, затем в конце хода на планшет; потеря при отсутствии клетки; обязательный возврат посетителя при наличии; получение при пустом вестибюле.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no` — согласованная механика стартовой репутации; награды и ID клеток перенесены в 17.6.

- **Исключения:** лишняя известность сгорает; художника можно продолжать рекламировать, но значение не растёт. Если все пять жетонов суперзвезды уже использованы, новый художник всё равно получает статус суперзвезды при достижении 19: выполняющий действие игрок получает 5 монет, работы становятся шедеврами и ограничения покупки сохраняются. Пропускается только выдача отсутствующего физического жетона. Статус хранится независимо от наличия жетона; повторная награда за того же художника запрещена.
- **События:** `ArtistBecameSuperstar`, `CoinsReceived`, `ArtworkBecameMasterpiece`.
- **Проверки:** точное достижение и переполнение; повторная реклама не выдаёт ещё 5 монет; при становлении суперзвездой в действии выдворения 5 монет получает только выдворенный игрок. Обычная покупка при известности 18 доводит художника до 19 и даёт покупаемой работе статус шедевра; шестая суперзвезда без жетона сохраняет все игровые эффекты и однократность награды.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.
- **Граница согласования:** согласованное уточнение взаимодействия зафиксировано в REVIEW-001 и REVIEW-004 (17.11); ранее согласованные части правила сохраняются.


### FAME-003 — Ограничение покупок у суперзвезды

- **Источник / фаза / триггер:** известность, с. 14; попытка покупки у суперзвезды.
- **Условия:** художник имеет статус суперзвезды.
- **Эффект:** обычная покупка запрещена.
- **Исключения:** владелец действующего контракта может совершить контрактную покупку; приобретённая у уже состоявшейся суперзвезды работа сразу становится шедевром.
- **События:** обычное событие покупки только при исключении.
- **Проверки:** обычная покупка отклонена; контрактная разрешена и приобретённая работа сразу является шедевром.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

## 15. Финальный подсчёт

### SCORE-001 — Порядок этапов

- **Источник / фаза / триггер:** финальный подсчёт, с. 15; `FinalScoringStarted`.
- **Условия:** дополнительный финальный раунд завершён.
- **Эффект:** последовательно считаются лидерство рынка, жетоны репутации, выставка, аукцион, карты куратора, карты арт-дилера, влияние, затем определяется победитель.
- **Исключения:** стартовый жетон репутации, оставшийся на третьей перегородке, перед подсчётом удаляется.
- **События:** событие каждого этапа и `FinalScoringCompleted`.
- **Проверки:** фиксированный порядок; повторный запуск не начисляет награды дважды.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### SCORE-002 — Лидерство на международном рынке

- **Источник / фаза / триггер:** финальный подсчёт, с. 15; первый этап.
- **Условия:** по каждой используемой колонке считаются все помощники игрока в верхней и нижней частях.
- **Эффект:** места получают напечатанные для колонки суммы; при ничьей суммы спорных мест складываются и делятся поровну с округлением вниз; игрок без помощников награду не получает.
- **Исключения:** каждая колонка считается независимо; отключённая колонка партии на двоих пропускается.
- **События:** `MarketLeadershipScored`.
- **Проверки:** явные 1/2/3 места; ничья за разные диапазоны мест; ноль помощников.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no` — выплаты всех трёх колонок перенесены в 17.6; механика ничьей остаётся черновой.

### SCORE-003 — Жетоны репутации и выставка

- **Источник / фаза / триггер:** финальный подсчёт, с. 15 и справочник с. 20.
- **Условия:** репутационные жетоны находятся на планшетах, работы — в выставочных залах.
- **Эффект:** каждый жетон применяет собственную формулу влияния/монет; затем каждая выставленная работа приносит текущую цену продажи.
- **Исключения:** жетон конвертации влияния в монеты считается первым, если это предписано его текстом.
- **События:** `ReputationTokensScored`, `ExhibitionScored`.
- **Проверки:** каждый тип жетона отдельным параметризованным сценарием; несколько работ разных художников.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no` — формулы и лицевые стороны 20 жетонов сопоставлены в 17.1 и 17.7; механика остаётся черновой.

### SCORE-004 — Аукцион выдающихся произведений

- **Источник / фаза / триггер:** финальный подсчёт, с. 15; этап аукциона.
- **Условия:** ставка игрока равна сумме значений рядов его помощников в нижней части рынка: 1, 3 или 6 за помощника. К аукциону допускаются только игроки с положительной ставкой; игроки с нулевой ставкой не получают работы.
- **Эффект:** игроки по убыванию ставки выбирают по одной доступной выдающейся работе, пока работы не закончатся; работа прикладывается к одной выбранной карте цели — куратора либо арт-дилера — и может помогать её выполнению. Игрок немедленно получает её цену как цену работы самого известного открытого художника того же жанра; если открытых художников этого жанра нет, цена равна 0. Полученная аукционная работа учитывается в числе всех приобретённых работ при разрешении ничьей по `SCORE-007`.
- **Исключения:** один игрок получает не более одной работы; ничья разрешается большей ставкой в колонке 3, затем 2, затем 1.
- **События:** `AuctionResolved`, `ExceptionalArtworkAwarded`, `CoinsReceived`.
- **Проверки:** разные ставки; все уровни разрешения ничьей; игроков больше, чем работ; ограничение одной работы; недопуск нулевой ставки, даже если остаются работы; цена 0 при отсутствии открытых художников жанра; выбор карты куратора или арт-дилера.
- **Статус:** `spec: draft` · `implementation: no` · `tests: no`.

### SCORE-005 — Карты целей

- **Источник / фаза / триггер:** финальный подсчёт, с. 15; после аукциона.
- **Условия:** известны приобретённые, выставленные, проданные и полученные на аукционе работы.
- **Эффект:** карта куратора начисляет монеты за указанные коллекции выставленных работ и не более одной аукционной работы; одна работа может входить в несколько целей. Карта арт-дилера начисляет монеты за указанные наборы проданных работ; приложенная к ней аукционная работа также может помогать выполнению целей. Одна аукционная работа прикладывается только к одной из двух карт и не учитывается одновременно для обеих; само приложение к карте арт-дилера не является продажей.
- **Исключения:** конкретные цели и суммы задаются данными карт. Каждая строка цели арт-дилера оплачивается за каждый отдельный полный набор работ; одна проданная работа не может использоваться в нескольких целях или нескольких наборах. Например, строка «две скульптуры → 10 монет» при четырёх разных проданных скульптурах даёт 20 монет. Для куратора ранее согласованное участие одной работы в разных целях сохраняется.
- **События:** `CuratorCardScored`, `DealerCardScored`.
- **Проверки:** каждая карта и цель; участие работы в нескольких целях куратора; запрет повторного использования проданной работы у арт-дилера; два отдельных набора из двух скульптур дают 20 монет, неполный набор не оплачивается; ограничения аукционной работы; использование на карте арт-дилера; запрет одновременного учёта на обеих картах.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no` — данные всех восьми карт, повторные выплаты за отдельные наборы арт-дилера и запрет повторного использования проданных работ согласованы.

### SCORE-006 — Финальная ценность влияния

- **Источник / фаза / триггер:** финальный подсчёт, с. 15; после карт целей.
- **Условия:** известна итоговая позиция на шкале влияния.
- **Эффект:** игрок получает число монет по таблице `INFLUENCE-DATA-001`, соответствующее наибольшей достигнутой денежной контрольной точке. При влиянии 34 выплачивается 18 монет, при 35 — 20; отдельной выплаты 19 монет на шкале нет.
- **Исключения:** значения символов монет, используемые во время игры, не определяют эту сумму напрямую.
- **События:** `InfluenceScored`.
- **Проверки:** границы каждого диапазона шкалы.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — чистый расчёт финальной выплаты реализован и протестирован; применение выплаты к игроку, событие `InfluenceScored` и оркестрация `final_scoring` отсутствуют.
- **Трассировка:** `calculateFinalInfluenceCoins` в [модуле подсчёта влияния](packages/game-engine/src/influence-scoring.ts); [тесты](packages/game-engine/test/influence-scoring.test.ts).

### SCORE-007 — Разрешение ничьей

- **Источник / фаза / триггер:** финальный подсчёт, с. 15; несколько лидеров по монетам.
- **Условия:** рассматриваются только претенденты с максимальным числом монет.
- **Эффект:** последовательно сравниваются: число всех приобретённых работ, включая полученные на аукционе; число посетителей в галерее; число помощников в игре, исключая безработных и удалённых.
- **Исключения:** если равенство сохраняется, все оставшиеся претенденты побеждают.
- **События:** `WinnerDetermined`.
- **Проверки:** ничья разрешается на каждом критерии; полное равенство даёт нескольких победителей; аукционная работа увеличивает число приобретённых работ независимо от выбранной карты цели.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — чистое последовательное сравнение переданных итоговых показателей реализовано и протестировано; вычисление этих показателей из `GameState`, включая учёт аукционной работы, интеграция с финальным подсчётом и событие `WinnerDetermined` отсутствуют.
- **Трассировка:** `determineWinners` в [модуле определения победителей](packages/game-engine/src/winner-determination.ts); [тесты](packages/game-engine/test/winner-determination.test.ts): победа по каждому критерию, полная ничья и сохранение порядка победителей.

- **Статус:** `spec: deferred` · `implementation: no` · `tests: no`.

### SOLO-004 — Окончание и цели

**Исправленные редакционные и технические несогласованности:**

- Ссылка на отсутствующий TICKET-003 заменена на существующие TICKET-001/002.
- TURN-002 согласован с ADR-003: подтверждение черновика не содержит событий ещё не применённых игровых действий.
- TURN-005 перечисляет события в уже согласованном порядке: последствия и выдворение, затем промежуточный доход, затем окончание и передача хода.
- Матрица реализации помечена как историческая; правка документа не выдаётся за повторную проверку 97 тестов.

**Требования к технической реализации, не новые вопросы правил:**

- Предусловия частей атомарного хода проверяются в порядке применения на промежуточных состояниях: управление до локации может дать нужные ресурсы, влияние колонки получается до оплаты ставки, помощник освобождает офис до награды найма. Проверка всего только по исходному снимку неверна; при ошибке откатывается весь ход и его события.
- Случайные операции во время игры (пополнение произведений и перемешивание заказов) ещё требуют отдельного детерминированного контракта; ADR-001 описывает только подготовку. Выбранные посетители из мешочка и случайно вытянутые посетители должны быть разными типами операций.
- Для начальной раскладки ещё нужны фиксированные ID/порядок четырёх локаций и стабильные ID экземпляров посетителей. Внутренние имена может определить разработчик, сохраняя пользовательскую терминологию.
- Команды дополнительных действий по наградам ORDER-ACTION и FAME-C должны включать все вложенные выборы, а не принимать только маркер категории. Модели наград и событий пока описаны спецификацией, не кодом.

## 19. Порядок согласования и реализации

1. Перенести согласованный справочник раздела 17 в данные движка и реализовать согласованный контракт полной подготовки `ADR-001`; решения `ADR-002`–`ADR-005` повторного согласования не требуют.
2. Согласовать и реализовать `SETUP-*` вместе с детерминированными тестами для 2/3/4 игроков.
3. Реализовать согласованную модель составного хода `ADR-003`, `TURN-002` и порядок эффектов `TURN-005`, затем согласовать оставшиеся `MGMT-*` и `EJECT-*`.
4. Последовательно реализовать действия локаций: художники, продажи, медиацентр, международный рынок.
5. Реализовать ресурсы, промежуточный подсчёт и известность.
6. Реализовать `END-*` и только затем `SCORE-*`.
7. Официальный одиночный вариант не начинать без отдельного изменения продуктового scope.
