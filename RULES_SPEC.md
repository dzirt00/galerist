# Реестр правил проекта «Галерист»

> Статус документа: игровая спецификация MVP и технические ADR согласованы; статусы реализации и тестов учитываются отдельно.

## 1. Назначение и границы

Этот файл содержит проверяемые контракты игрового движка. Он не воспроизводит текст или оформление исходного руководства. Формулировки ниже являются кратким техническим пересказом механик.

Источником служит русское руководство к настольной игре, разделы «Подготовка к игре» — «Финальный подсчёт» и «Одиночная игра». Номера страниц указаны по печатной нумерации источника.

В продуктовый MVP входят партии на 2–4 места, занятые людьми или ботами. Официальный одиночный вариант с нейтральным соперником вынесен в отдельный отложенный раздел и не должен смешиваться с режимом «один человек против ботов».

## 2. Статусы и трассировка

Каждая запись содержит:

- `spec`: `draft`, `needs_decision`, `needs_data`, `approved` или `deferred`; `needs_data` означает отсутствие проверенных справочных данных при отдельно согласуемой механике;
- `implementation`: `no`, `partial` или `yes`;
- `tests`: `no`, `partial` или `yes`.

После появления реализации в поле статуса добавляется ссылка на модуль, а после появления тестов — имя теста или сценария. Значение `partial` означает, что существующий код совпадает лишь с частью контракта и ещё не реализует правило целиком.

События перечислены как доменные имена. Для реализованных команд их TypeScript API фиксируется ADR-007: команда возвращает неизменяемый `GameTransition<TState>` в форме `{ state, events }`.

### ADR-001 — Seed и выбор первого игрока минимального движка

- **Согласованная часть:** одинаковые seed, порядок игроков и версии правил, компонентов и алгоритма дают одинаковый результат случайной подготовки. При одинаковых последующих выборах игроков результат полной подготовки также совпадает. Сам seed не определяет решения игроков, например стартовую локацию.
- **Seed:** `createGame` принимает только безопасное целое число, включая отрицательные значения. При нарушении проверка отклоняет вызов с ошибкой `Seed must be a safe integer`; проверки числа игроков и уникальности ID сохраняются.
- **Выбор:** `firstPlayerIndex` равен неотрицательному остатку `seed` по `players.length`. `startGame` выбирает `players[firstPlayerIndex].id` и устанавливает этот ID одновременно в `firstPlayerId` и `activePlayerId`. Для трёх игроков seed `0`, `1`, `2`, `3` и `-1` дают индексы `0`, `1`, `2`, `0` и `2` соответственно.
- **Порядок и воспроизводимость:** `players` остаётся порядком мест по часовой стрелке согласно ADR-004; перестановки игроков, `Math.random` и внешнего изменяемого состояния нет. Одинаковые seed и порядок игроков дают одного первого игрока.
- **Граница подготовки:** в `setup` нет `firstPlayerId`. Выбор происходит при `startGame`, который создаёт новый замороженный корневой объект с `phase: regular_play`, `status: in_progress`, `round: 1`, не изменяя входное setup-состояние.
- **Алгоритм полной подготовки (`setup-rng-v1`):** справочные наборы содержат устойчивые уникальные ASCII ID для каждого экземпляра компонента и явный порядок жанров, категорий, клеток и локаций. До случайного отбора каждый набор сортируется по ID в порядке ASCII. `rulesVersion` для этой согласованной редакции равно `galerist-rules-2026-09-15-v1`; изменение данных меняет `componentsVersion`, изменение правил — `rulesVersion`, изменение алгоритма или порядка операций — `setupAlgorithmVersion`.
- **Поток случайных значений:** для каждого именованного этапа ведётся собственный счётчик, начиная с 0. На очередном шаге вычисляется SHA-256 от UTF-8 строки компактного JSON-массива `["setup-rng-v1", rulesVersion, componentsVersion, seedString, playerIds, stageId, counterString]`. Строки чисел записываются в десятичной форме без ведущих нулей; seed `-0` нормализуется в `"0"`; массив ID игроков сохраняет порядок мест. Сериализация строк соответствует `JSON.stringify`, пробелов между элементами нет. Первые четыре байта хеша читаются как беззнаковое 32-битное число в порядке от старшего байта к младшему; счётчик увеличивается после каждого хеша.
- **Равномерный выбор:** для выбора индекса из `n` элементов, где `1 ≤ n ≤ 2^32`, вычисляется `limit = floor(2^32 / n) * n`; значения `x ≥ limit` пропускаются, иначе индекс равен `x % n`. Пустой набор не допускает выбор. Перемешивание выполняется перестановками: для `i` от `length - 1` до 1 выбрать `j` из `0…i` и обменять элементы `i` и `j`. Пустой набор и набор из одного элемента не потребляют значений. Отбор без возвращения берёт первые нужные элементы перемешанного набора.
- **Публичная инфраструктура RNG:** до реализации setup-пайплайна движок экспортирует `createSetupRng({ rulesVersion, componentsVersion, seed, playerIds })`, возвращающий `SetupRng`, и его методы `nextUint32(stageId)`, `chooseIndex(stageId, itemCount)` и `shuffle(stageId, items)`. Счётчики принадлежат экземпляру `SetupRng` и независимы по непустому `stageId`. `chooseIndex` отклоняет нецелые размеры, размеры меньше 1 и больше `2^32`; отклонённые при rejection sampling хеши расходуют счётчик. `shuffle` использует тот же поток, возвращает новый замороженный массив-перестановку с исходными ссылками на элементы и не изменяет и не замораживает входной массив либо его элементы. SHA-256 берётся из штатного `node:crypto`; новая зависимость не нужна. Инфраструктура не создаёт `GameState` и не выполняет раскладку компонентов.
- **Lifecycle полной подготовки:** `createGame` принимает внешний непустой `gameId`, не выводит идентичность партии из seed и сразу создаёт полный серверный снимок версии схемы `3` с детерминированной раскладкой, `phase: 'setup'`, `status: 'setup'`, `setupStage: 'choosing_starting_locations'`. В setup нет `firstPlayerId`: для обратного порядка выбора вычисляется тот же индекс, но поле первого игрока появляется лишь при `startGame`. Единственная команда выбора — `chooseStartingLocation(state, playerId, locationId)`; она допустима только для текущего выбирающего игрока и свободной локации. Порядок выбора является обратным полному порядку обычного хода, начинающемуся с первого игрока. После последнего корректного выбора `setupStage` становится `'complete'`; `startGame` принимает только такой setup, заново вычисляет первого игрока без потребления RNG и создаёт `regular_play`.
- **Порядок подготовки:** (1) сформировать запасы для числа игроков; (2) перемешать заказы, этап `orders`, выложить четыре; (3) перемешать всех художников, этап `artists`, последовательно брать первого для каждой ещё незаполненной пары жанр/категория по `SETUP-004`; (4) перемешать бонусы, этап `artist-bonuses`, раздать закрытым художникам в фиксированном порядке клеток, затем выделить красным художникам коллекционеров; (5) перемешать оставшийся мешочек посетителей, этап `visitors`, и брать посетителей с начала этой последовательности; (6) отдельно перемешать работы каждого жанра, этап `artworks/<genreId>`, в порядке жанров из данных; отложить верхние работы, затем наполнить новые верхние работы посетителями в том же порядке жанров; (7) перемешать репутацию, этап `reputation`, заполнить используемые ячейки рынка сверху вниз по рядам, внутри ряда слева направо, затем локации в порядке данных; (8) перемешать четыре отложенные работы, этап `auction-artworks`, и выбрать число по `SETUP-009`; (9) взять четырёх посетителей на площадь, затем по одному в вестибюли в порядке `players`; (10) определить индекс первого игрока прежней формулой без расхода случайных значений; (11) независимо перемешать колоды целей, этапы `curator-goals` и `dealer-goals`, раздать по одной карте каждого типа в порядке `players`; (12) выполнить записываемые выборы стартовых локаций в обратном порядке хода. Нерандомизированные запасы и планшеты размещаются по соответствующим `SETUP-*`.
- **Восстановление и скрытые данные:** серверный снимок (`GameState`) хранит `stateSchemaVersion`, seed, версии, порядок игроков, порядки оставшихся колод/мешочка, все разданные цели и выборы подготовки. `restoreGameState` проверяет границу JSON-снимка, согласованность фазы, статуса и ссылок на игроков, возвращает собственную глубоко замороженную копию и отклоняет неизвестную версию схемы. Для повторного запуска подготовки используются те же входы и версии. `projectGameForViewer(state, viewerId)` принимает ID игрока или `null` для наблюдателя и возвращает публичную проекцию: в ней нет seed, версий, ID и порядков скрытых колод или мешочка. Игрок видит только свои две карты целей; наблюдатель до `final_scoring` не видит целей, а начиная с `final_scoring` все цели видны всем. `projectEventsForViewer` скрывает `FirstPlayerSelected` во время setup и приватные события раздачи целей от посторонних. Проекция показывает текущего выбирающего игрока, занятые и свободные локации и открытую раскладку; скрытые компоненты показываются только количеством. Контракт случайных операций во время игры определён в `ADR-008`; подготовка не использует `Math.random`, часы или внешнее изменяемое состояние.
- **Граница минимального и полного движка:** `startGame` добавляет `firstPlayerId` только при старте. Полная подготовка вычисляет тот же индекс заранее для обратного порядка выбора локаций и не начинает обычные ходы до завершения всех выборов. Серверный setup-пайплайн, записываемый выбор стартовых локаций, setup-события и приватная проекция реализованы.
- **Проверки:** совпадение раскладки при одинаковых входах и итогового setup при одинаковых выборах; фиксированные эталонные раскладки для 2/3/4 игроков, включая отрицательный seed; отсутствие дубликатов/потерь компонентов; независимость от порядка входных справочных массивов после сортировки; продолжение из восстановленного снимка; отсутствие скрытых раздач, seed и преждевременно раскрытого первого игрока в публичных проекциях.
- **Трассировка:** `createGame` в [оркестраторе setup](packages/game-engine/src/game-setup.ts), `startGame` в [lifecycle партии](packages/game-engine/src/game-lifecycle.ts), `chooseStartingLocation` в [команде выбора](packages/game-engine/src/choose-starting-location.ts), оболочка в [модуле событий](packages/game-engine/src/game-events.ts), восстановление в [валидации снимка](packages/game-engine/src/game-state-validation.ts), публичные представления в [проекции состояния](packages/game-engine/src/game-projection.ts) и [проекции событий](packages/game-engine/src/game-event-projection.ts); [сквозные тесты setup](packages/game-engine/test/setup-pipeline.test.ts): события, эталонные раскладки 2/3/4 игроков, одинаковые выборы и восстановленный снимок; [тесты границы](packages/game-engine/test/engine-boundary.test.ts): внешний ID, версия схемы, восстановление и скрытые события; инфраструктура `setup-rng-v1` проверена в [тестах RNG](packages/game-engine/test/setup-rng.test.ts).

### ADR-002 — Представление фаз жизненного цикла

- **Статус:** `approved`.
- **Решение:** `GameState` представляется дискриминируемым объединением шести вариантов по полю `phase`. Существующее поле `status` сохраняется как укрупнённый статус партии и в каждом варианте статически согласуется с фазой.

| `phase`                | `status`      | `activePlayerId`    | Инварианты фазы                                                                                                                       |
| ---------------------- | ------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `setup`                | `setup`       | `null`              | Раунд равен 0; подготовка ещё не перешла к обычным ходам.                                                                             |
| `regular_play`         | `in_progress` | ID участника партии | Раунд положительный; определён неизменный первый игрок.                                                                               |
| `ending_current_round` | `in_progress` | ID участника партии | Сохранён `endTriggeredRound`; оставшиеся игроки заканчивают обычный текущий круг.                                                     |
| `final_round`          | `in_progress` | ID участника партии | Сохранён `endTriggeredRound`; каждый игрок получает ровно один ход, начиная с первого игрока.                                         |
| `final_scoring`        | `in_progress` | `null`              | Ходы запрещены; номер раунда сохраняет номер завершённого финального круга.                                                           |
| `finished`             | `finished`    | `null`              | Финальный подсчёт завершён; номер последнего завершённого раунда и данные срабатывания конца сохраняются для восстановления и аудита. |

В движке `startGame` добавляет `firstPlayerId`, принадлежащий `players`, по согласованному seed-контракту ADR-001; в `setup` этого поля нет. Полная seed-детерминированная подготовка ADR-001 реализована. `endTriggeredRound` существует только в вариантах начиная с `ending_current_round`, поэтому состояние до срабатывания конца не может содержать это поле случайно.

`startGame` допустим только для варианта `setup` и создаёт `regular_play` с раундом 1 и активным первым игроком. `advanceTurn` сохраняет обязательную проверку `status === 'in_progress'`, но дополнительно разрешён только для `regular_play`, `ending_current_round` и `final_round`; вариант `final_scoring` не допускает смену игрока.

Все три фазы с ходами используют один порядок мест `players` по часовой стрелке. Граница круга определяется переходом следующего игрока к `firstPlayerId`. В `ending_current_round` эта граница начинает `final_round` с первого игрока и увеличивает номер раунда. После хода последнего игрока `final_round` не передаёт ход первому повторно, а переходит в `final_scoring` и очищает `activePlayerId`.

Переход в `finished` допустим только после завершения `final_scoring`; безусловный публичный переход из обычной игры в `finished` не предусматривается. Каждая смена фазы должна иметь отдельное доменное событие, а сериализованный снимок должен содержать дискриминант и данные своего варианта. Это позволяет проверять снимок при загрузке и однозначно восстанавливать фазу повтором серверного журнала событий. Формат подсчёта и итоговой таблицы в ADR-002 не определяется.

В [текущем модуле](packages/game-engine/src/index.ts) реализована последовательность `setup` → `regular_play` → `ending_current_round` → `final_round` → `final_scoring`. Завершение запускается явным вызовом `triggerGameEnd`, без оценки игровых индикаторов. `prepareTurn` принимает ход только в `regular_play`, `ending_current_round` и `final_round`, дополнительно проверяя `status: in_progress` при каждом вызове. Тип `FinishedGameState` существует, но переход в `finished` и сам финальный подсчёт не реализованы. Доменные события setup и старта партии реализованы по ADR-007; события остальных фаз, runtime-проверка загружаемых снимков и восстановление по журналу ещё не реализованы.

### ADR-003 — Команды и черновик составного хода

- **Статус:** `approved`.
- **Граница состояния:** `TurnDraft` является отдельным неизменяемым значением и не входит в `GameState`. Формирование и подтверждение черновика не меняют состояние партии; игровые эффекты возникают только при применении подтверждённой команды.
- **Формат черновика:** минимальные поля — `playerId`, необязательные до подтверждения `movement` и `locationAction`, а также не более одного `management`. Выбор управления хранит `timing: 'before_location' | 'after_location'` и саму команду управления.
- **Формат подтверждённой команды:** `ConfirmedTurnCommand` содержит `type: 'perform_turn'`, `playerId`, обязательные `movement` и `locationAction` и необязательный `management`. Перемещение всегда выполняется первым; `timing` определяет взаимный порядок управления и действия локации.
- **Подготовленный план:** `PreparedTurn` — техническое дополнение API для подготовки подтверждённой команды к будущему исполнению. Его `steps` имеет тип `TurnExecutionSteps`: без управления это `[movement, locationAction]`, с `before_location` — `[movement, management.command, locationAction]`, с `after_location` — `[movement, locationAction, management.command]`. План содержит команды, а не доменные события.
- **Редактирование:** публичный `TurnDraftEdit` является дискриминируемым объединением операций `set_movement`, `set_location_action`, `set_management_action` и `clear_management_action`. Повторная установка заменяет соответствующее единственное поле и не накапливает действия.
- **Публичные функции:** `createTurnDraft(playerId)` создаёт пустой черновик; `updateTurnDraft(draft, edit)` возвращает новый черновик; `confirmTurnDraft(draft)` возвращает `ConfirmedTurnCommand`; `prepareTurn(state, command)` возвращает `PreparedTurn`. Будущий `applyTurn(state, command)` должен возвращать новый `GameState`.
- **Проверка и применение:** `confirmTurnDraft` отклоняет черновик без перемещения или действия локации. Единственное поле `management` структурно запрещает два действия управления. `prepareTurn` при каждом вызове проверяет актуальные фазу, статус, принадлежность активного игрока партии, совпадение `command.playerId` с ним и наличие обязательных частей, затем возвращает новый независимый замороженный план. Эта функция не проверяет игровые предусловия конкретных действий, не резервирует и не применяет ход. Будущий `applyTurn` обязан заново проверить актуальное состояние и все зависящие от него предусловия, применить части в согласованном порядке как одну атомарную операцию и при отклонении не менять входной снимок.
- **Выдворение:** возможности выдворения не входят в `TurnDraft` или `ConfirmedTurnCommand`. В будущем они фиксируются в состоянии после применения обычного хода и разрешаются отдельными командами до `advanceTurn`; точный формат этих команд и ожидающих возможностей определяется при реализации `EJECT-*`.
- **Граница контракта:** `MovementCommand`, `LocationActionCommand` и `ManagementActionCommand` здесь обозначают категории команд. Их конкретные дискриминированные варианты, игровые данные и доменные события этим ADR не утверждаются.
- **Тестирование:** отдельно проверяются неизменяемое редактирование черновика, его структурное подтверждение, state-зависимая подготовка, три точных порядка команд, независимость и заморозка плана, повторная проверка после смены активного игрока, а в будущем — атомарность применения и отсутствие изменения исходного состояния при ошибке.
- **Текущее состояние:** в [модуле движка](packages/game-engine/src/index.ts) реализованы категорийные маркеры команд, `TurnDraft`, `TurnDraftEdit`, `ConfirmedTurnCommand`, `PreparedTurn`, `TurnExecutionSteps`, создание, неизменяемое редактирование, структурное подтверждение черновика и подготовка плана по актуальному снимку. [Тесты черновика](packages/game-engine/test/turn-draft.test.ts) и [тесты подготовки хода](packages/game-engine/test/turn-preparation.test.ts) проверяют три порядка, все разрешённые и запрещённые фазы, статус, активного и командующего игроков, обязательные части на JS-границе, сохранность входов, независимую заморозку результата, повторные вызовы, повторную проверку после `advanceTurn` и полный путь от черновика до плана. `applyTurn`, игровые эффекты, полная проверка игровых предусловий и доменные события отсутствуют; существующий `advanceTurn` выполняет только ротацию активного игрока и не считается применением составного хода.

### ADR-007 — Результат команды с доменными событиями

- **Статус:** `approved`.
- **Решение:** команда, создающая доменные события, возвращает `GameTransition<TState>` в форме `{ state, events }`. Состояние не хранит журнал событий. Корень перехода, новое состояние, массив событий и каждое событие глубоко заморожены.
- **Порядок:** `events` хранит события в порядке завершения эффектов команды. Отклонённая команда выбрасывает ошибку, не меняет вход и не возвращает частичный переход.
- **Трассировка:** `GameEvent`, `GameTransition` и `freezeTransition` в [модуле событий](packages/game-engine/src/game-events.ts); setup-команды в [lifecycle партии](packages/game-engine/src/game-lifecycle.ts) и [команде выбора локации](packages/game-engine/src/choose-starting-location.ts); [сквозные тесты](packages/game-engine/test/setup-pipeline.test.ts).

### ADR-008 — Детерминированная случайность во время партии

- **Статус:** `approved`.
- **Граница:** уже перемешанные при setup стопки произведений и `visitorBag` не перемешиваются повторно. `ARTWORK-006` снимает следующую работу и следующих посетителей из сохранённых последовательностей, поэтому отдельного случайного выбора во время пополнения рынка нет. Новая случайная операция MVP возникает при перемешивании сброшенных заказов по `ORDER-002`.
- **Состояние:** серверный `GameState` хранит скрытое поле `runtimeRng: RuntimeRngState` с полями `runtimeRngVersion: 'runtime-rng-v1'` и `runtimeRngCounters`, содержащим независимые неотрицательные безопасные целые счётчики по `streamId`. Начальное состояние создаётся вместе с игрой; использованные счётчики входят в снимок, проверяются при восстановлении и не попадают в публичную проекцию.
- **Потоки:** для переработки заказов используется поток `orders/recycle`. Будущая случайная операция получает отдельный устойчивый `streamId`, чтобы расход одного потока не менял результаты другого.
- **Генерация:** очередное 32-битное значение вычисляется тем же SHA-256 и rejection-sampling контрактом, что в `ADR-001`, но с доменом `runtime-rng-v1`: компактный JSON-массив `["runtime-rng-v1", rulesVersion, componentsVersion, seedString, playerIds, streamId, counterString]`. Перемешивание использует тот же Fisher–Yates. `Math.random`, часы и внешнее изменяемое состояние запрещены.
- **Применение:** успешная атомарная команда сохраняет увеличенные счётчики в новом состоянии. Отклонённая команда не расходует случайные значения и не меняет вход. Одинаковые `GameState` и команда дают одинаковые состояние и события; продолжение из восстановленного снимка сохраняет последовательность.
- **Версионирование:** добавление `runtimeRng` в сохраняемое состояние требует увеличения `stateSchemaVersion` при реализации. Изменение формулы, сериализации, счётчиков или алгоритма перемешивания требует новой версии runtime-RNG; изменение правил и данных по-прежнему отражается в `rulesVersion` и `componentsVersion`.
- **Проверки:** одинаковый результат после восстановления; независимость потоков; несколько последовательных переработок заказов; расход счётчика только успешной командой; отсутствие runtime-RNG и скрытого порядка заказов в публичной проекции.

## 4. Общие инварианты

### CORE-001 — Число участников MVP

- **Источник / фаза / триггер:** границы продукта и подготовка, с. 2; создание партии.
- **Условия:** обычная онлайн-партия содержит 2, 3 или 4 места.
- **Эффект:** конфигурация и список игроков содержат одинаковое допустимое число участников.
- **Исключения:** официальный одиночный вариант не является партией с одним обычным местом.
- **События:** `GameCreated` после успешной полной подготовки.
- **Проверки:** принять 2/3/4 места; отклонить другое число и несовпадение конфигурации со списком.
- **Статус:** `spec: approved` · `implementation: yes` · `tests: yes`.
- **Трассировка:** runtime-проверка допустимых значений и совпадения со списком игроков в `createGame` в [оркестраторе setup](packages/game-engine/src/game-setup.ts); [тесты](packages/game-engine/test/game-lifecycle.test.ts): параметризованные `отклоняет согласованную конфигурацию на $playerCount игроков`, `принимает допустимую конфигурацию на %i игроков` и сценарий несовпадения числа игроков с конфигурацией.

### CORE-002 — Ограниченность компонентов

- **Источник / фаза / триггер:** подготовка, с. 2; любая попытка получить компонент.
- **Условия:** монеты не ограничены; остальные физические компоненты ограничены текущим запасом.
- **Эффект:** доступный компонент перемещается из соответствующего запаса.
- **Исключения:** если компонент закончился, игрок его не получает; специальные правила билетов описаны в `TICKET-002`.
- **События:** событие получения создаётся только для фактически полученного количества.
- **Проверки:** получение из непустого запаса; пустой запас не создаёт компонент и не уводит количество ниже нуля.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no`.

### CORE-003 — Цель и победитель

- **Источник / фаза / триггер:** обзор, с. 4; завершение финального подсчёта.
- **Условия:** все этапы финального подсчёта выполнены.
- **Эффект:** победителем становится участник с наибольшим итоговым количеством монет; ничьи разрешаются по `SCORE-007`.

- **Проверки:** единственный лидер; полная ничья после всех дополнительных критериев.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — `completeFinalScoring` после финальной выплаты за влияние проверяет полный набор переданных кандидатов и их актуальные монеты, определяет победителей, сохраняет `winnerIds`, создаёт `WinnerDetermined` и `FinalScoringCompleted` и переводит партию в `finished`. ### CORE-004 — Неизменяемые переходы движка

- **Источник / фаза / триггер:** технический принцип проекта; любой переход состояния.
- **Условия:** движок получает снимок `GameState`.
- **Эффект:** успешный переход возвращает новый неизменяемый корневой объект, а отклонённый вызов не меняет входной снимок.
- **Исключения:** ссылки на неизменённые вложенные данные могут сохраняться, если контракт перехода это разрешает.
- **События:** отсутствуют при отклонении.
- **Проверки:** сравнить вход с глубокой копией после успешного и отклонённого вызова; проверить заморозку результата.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — реализованные публичные переходы setup, lifecycle, ресурсов и финального подсчёта возвращают новое состояние, не изменяют вход и глубоко замораживают результат через общий контракт `GameTransition`. Статус остаётся `partial`, пока не реализованы применение составного хода и остальные игровые эффекты.
- **Трассировка:** общий `freezeTransition` в [модуле событий](packages/game-engine/src/game-events.ts); неизменяемость setup-пайплайна проверена в [интеграционных тестах подготовки](packages/game-engine/test/setup-pipeline.test.ts), а переходов lifecycle и финального подсчёта — в [тестах жизненного цикла](packages/game-engine/test/game-lifecycle.test.ts) и [интеграционных тестах завершения](packages/game-engine/test/final-scoring-completion.test.ts).
- **Трассировка:** неизменяемость `prepareTurn` проверена сценариями возврата нового замороженного плана, всеми параметризованными сценариями отклонения и повторной подготовки равных независимых планов в [тестах подготовки хода](packages/game-engine/test/turn-preparation.test.ts). Статус остаётся `partial`, пока не реализованы остальные переходы и применение игровых эффектов.
- **Трассировка:** неизменяемость `completeFinalScoring`, включая mutable-вход, отклонённые команды и глубокую заморозку независимого результата, проверена в [интеграционных тестах завершения](packages/game-engine/test/final-scoring-completion.test.ts).

### SETUP-002 — Начальные влияние и монеты

- **Источник / фаза / триггер:** подготовка, с. 2–3; создание партии.

### SETUP-004 — Выбор художников

### SETUP-012 — Планшет и стартовая локация игрока

- **Источник / фаза / триггер:** подготовка, с. 3; после выбора первого игрока.
- **Условия:** для каждого игрока доступны 10 помощников, планшет, галерист и карты целей. Доступны четыре стартовые локации с устойчивыми ASCII ID в фиксированном порядке данных: `LOC-ARTISTS_COLONY` («Сообщество художников»), `LOC-MEDIA_CENTER` («Медиацентр»), `LOC-INTERNATIONAL_MARKET` («Международный рынок»), `LOC-SALES_OFFICE` («Офис продаж»).
- **Эффект:** восемь помощников заполняют очередь безработных, два занимают любые рабочие места офиса. До выбора стартовых локаций каждый игрок получает ровно по одной случайной карте куратора и арт-дилера без выбора из нескольких карт. Команда `chooseStartingLocation(state, playerId, locationId)` принимает выбор только текущего игрока из обратного порядка обычного хода и только для ещё не занятой локации. Она размещает там галериста и переносит жетон репутации локации на третью перегородку. После последнего выбора setup имеет `setupStage: 'complete'`.
- **Исключения:** оставшиеся у локаций жетоны репутации удаляются после выбора всех игроков. Карты целей доступны владельцу до его выбора локации и скрыты от остальных игроков до финального подсчёта; сервер хранит полный набор данных, а представление для каждого игрока исключает чужие цели и скрытые колоды.
- **События:** `PlayerBoardPrepared`, `StartingLocationChosen`, `PrivateGoalsDealt`.
- **Проверки:** обратный порядок выбора; запрет занятой локации; по 10 помощников, две занятые офисные клетки; ровно одна случайная карта каждого типа без выбора; владелец видит цели до выбора локации, соперники — только при финальном подсчёте.
- **Статус:** `spec: approved` · `implementation: yes` · `tests: yes` — `createGame` раздаёт приватные цели, создаёт планшеты и начинает выбор локаций. `chooseStartingLocation` валидирует текущего игрока и свободную локацию, переносит жетон, переключает игрока и завершает setup с очисткой оставшихся жетонов. `projectGameForViewer` скрывает seed, версии, закрытые порядки и чужие цели до финального подсчёта. Реализованы `PlayerBoardPrepared`, `PrivateGoalsDealt` и `StartingLocationChosen`.
- **Трассировка:** [каталог компонентов](packages/game-engine/src/component-catalog.ts), [данные карт целей](packages/game-engine/src/goal-card-catalog.ts), [подготовка приватных целей](packages/game-engine/src/setup-goals.ts), [подготовка планшетов](packages/game-engine/src/player-boards.ts), [команда выбора](packages/game-engine/src/choose-starting-location.ts), setup-поля и поля `privateGoals`/`playerBoards` в [типах состояния](packages/game-engine/src/types.ts), интеграция и запрет преждевременного старта в [lifecycle партии](packages/game-engine/src/game-lifecycle.ts); [тесты каталога](packages/game-engine/test/component-catalog.test.ts), [тесты целей](packages/game-engine/test/setup-goals.test.ts), [тесты планшетов](packages/game-engine/test/player-boards.test.ts), [тесты выбора локаций](packages/game-engine/test/choose-starting-location.test.ts): порядок для 2/3/4 игроков, перенос жетона, переключение выбирающего, очистка оставшихся жетонов, сохранение свободных локаций, ошибочные команды, глубокая заморозка и граница `startGame`; [интеграционные тесты lifecycle](packages/game-engine/test/game-lifecycle.test.ts): сохранение подготовленных компонентов после полного setup и удаление временных setup-полей при старте.

## 6. Раунды, ход и передача инициативы

### TURN-001 — Начало обычной партии

- **Источник / фаза / триггер:** процесс игры, с. 5; завершение подготовки.
- **Условия:** подготовка полностью завершена и первый игрок определён.
- **Эффект:** начинается первый раунд, активным становится первый игрок.
- **Исключения:** запуск неполной или уже начатой партии запрещён.
- **События:** `GameStarted`, `RoundStarted`, `TurnStarted`.
- **Проверки:** корректное начало; отклонение повторного запуска без изменения состояния.
- **Статус:** `spec: approved` · `implementation: yes` · `tests: yes` — `startGame` принимает только setup с `setupStage: 'complete'`, запускает первый раунд с seed-выбором совпадающих первого и активного игроков, запрещает преждевременный или повторный запуск и возвращает `GameStarted`, `RoundStarted`, `TurnStarted`.
- **Трассировка:** `startGame` в [lifecycle партии](packages/game-engine/src/game-lifecycle.ts); [тесты выбора локаций](packages/game-engine/test/choose-starting-location.test.ts): запрет старта до завершения setup и успешный старт после него; [интеграционные тесты](packages/game-engine/test/game-lifecycle.test.ts): переход в `regular_play`, запуск без изменения исходного состояния, отклонение повторного запуска и `выбирает $expectedPlayer при seed: $seed`.

### TURN-002 — Состав обычного хода

- **Источник / фаза / триггер:** процесс игры и действия управления, с. 5; начало хода.
- **Условия:** ход принадлежит активному игроку.
- **Эффект:** игрок обязательно перемещает галериста и выполняет одно действие новой локации; дополнительно он может выполнить не более одного действия управления до либо после действия локации.
- **Исключения:** действие управления необязательно; порядок фиксируется выбранной последовательностью действий.
- **События:** подтверждение черновика само по себе не создаёт игровых эффектов или доменных событий по ADR-003. При успешном атомарном применении хода создаётся упорядоченный набор событий выполненных действий; отклонённый ход не создаёт событий.
- **Проверки:** варианты управление→локация, локация→управление и только локация; отклонить два действия управления или отсутствие действия локации.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — по ADR-003 в [модуле движка](packages/game-engine/src/index.ts) реализованы создание, неизменяемое редактирование и структурное подтверждение черновика, а также `prepareTurn`: проверка фазы и активного игрока и построение независимого замороженного плана в трёх допустимых порядках. В [тестах черновика](packages/game-engine/test/turn-draft.test.ts) и [тестах подготовки хода](packages/game-engine/test/turn-preparation.test.ts) проверены операции с черновиком, три порядка плана, разрешённые и запрещённые фазы, принадлежность хода, обязательные части, неизменяемость, повторная подготовка, повторная проверка после `advanceTurn` и сквозной сценарий. На runtime-границе `prepareTurn` отклоняет неизвестный, отсутствующий или null timing заданного управления и отсутствующую, undefined или null команду управления; отказ сохраняет значения и признаки заморозки входов. `applyTurn`, игровые предусловия и эффекты, доменные события и атомарность применения ещё отсутствуют.

- **Трассировка runtime-проверок управления:** [prepareTurn](packages/game-engine/src/turn-preparation.ts); [тесты подготовки хода](packages/game-engine/test/turn-preparation.test.ts): недопустимый и отсутствующий timing, отсутствующая или null команда, сохранность входов при отказе.

### TURN-003 — Перемещение галериста

- **Источник / фаза / триггер:** действия локаций, с. 5; обязательное перемещение хода.
- **Условия:** если галерист находится в локации, он обязан перейти в другую локацию; если находится дома в галерее, может выбрать любую локацию.
- **Эффект:** галерист занимает выбранную локацию и открывает одно из двух её действий.
- **Исключения:** остаться в прежней локации нельзя.
- **События:** `GalleristMoved`.
- **Проверки:** переход между разными локациями; отклонение прежней локации; выход из домашней галереи в любую локацию.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no`.

### TURN-004 — Оставление помощника

- **Источник / фаза / триггер:** действия локаций, с. 5; перемещение между двумя локациями.
- **Условия:** у игрока есть помощник в офисе или другой локации.
- **Эффект:** перед уходом игрок может оставить ровно одного своего помощника в покидаемой локации, переместив его из допустимого источника.
- **Исключения:** при отсутствии доступного помощника эффект недоступен; помощник не обязателен.
- **События:** `AssistantLeftAtLocation`.
- **Проверки:** помощник из офиса и другой локации; отсутствие помощника; попытка оставить больше одного.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no`.

### TURN-005 — Разрешение последствий и следующий игрок

- **Источник / фаза / триггер:** процесс игры, с. 5–6; окончание действий активного игрока.
- **Условия:** действие локации и выбранное действие управления завершены.
- **Эффект:** опустошение первой цветной стопки билетов только назначает промежуточный подсчёт и не начисляет доход немедленно. После действий активного игрока разрешается получение стартовой репутации, затем дополнительные действия выдворения и возникшие при них отложенные эффекты. После этого выполняется назначенный промежуточный подсчёт по составу галерей на момент начисления, и лишь затем ход переходит следующему участнику по кругу. Выдворенный игрок не получает новый обычный ход. Если первая стопка билетов опустела в действии выдворения, подсчёт проводится в конце этого же обычного хода до передачи инициативы.
- **Исключения:** в дополнительном финальном раунде действия выдворения подавлены по `END-004`.
- **События:** события получения стартовой репутации, действий выдворения и остальных отложенных эффектов, затем события назначенного промежуточного подсчёта; после их завершения `TurnEnded` и передача инициативы с `TurnStarted` либо переходом фазы по END-005.
- **Проверки:** выдворение не меняет круговой порядок; передача хода происходит после всех отложенных эффектов.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — круговой порядок и начисление промежуточного дохода после действий выдворения согласованы; `advanceTurn` реализует ротацию и создаёт упорядоченные публичные события `TurnEnded` и `TurnStarted`, а перед `FinalScoringStarted` создаёт только `TurnEnded`. Игровые эффекты, выдворение и промежуточный подсчёт ещё отсутствуют.
- **Трассировка:** `advanceTurn` в [модуле жизненного цикла](packages/game-engine/src/game-lifecycle.ts), `TurnEnded` и `TurnStarted` в [событиях движка](packages/game-engine/src/game-events.ts); [интеграционные тесты](packages/game-engine/test/game-lifecycle.test.ts): `передаёт ход следующему игроку без изменения номера раунда`, `завершает прежний и начинает новый ход при входе в финальный раунд`, `передаёт ход в финальном раунде`, начало нового раунда с первым игроком при трёх и четырёх участниках и `переходы хода и увеличение раунда при первом игроке, отличном от players[0]`. Составной ход, выдворение и отложенные эффекты пока не проверяются.

### TURN-006 — Граница раунда

- **Источник / фаза / триггер:** процесс и конец игры, с. 5; передача хода первому игроку.
- **Условия:** завершён ход игрока, стоящего непосредственно перед первым игроком в круговом порядке.
- **Эффект:** текущий раунд заканчивается, номер раунда увеличивается и начинается ход первого игрока.
- **Исключения:** согласно ADR-002, в `ending_current_round` эта граница начинает `final_round`; в `final_round` она переводит партию в `final_scoring` без увеличения номера раунда и без повторной передачи хода первому игроку.
- **События:** `RoundEnded`, `RoundStarted`.
- **Проверки:** полный круг для 2/3/4 игроков; неполный круг не увеличивает номер; при первом игроке, отличном от `players[0]`, номер увеличивается только при возврате к `firstPlayerId`.
- **Статус:** `spec: approved` · `implementation: yes` · `tests: yes` — `advanceTurn` определяет границу по возврату к `firstPlayerId`, завершает текущий раунд, увеличивает номер и начинает следующий раунд; при завершении `final_round` номер не увеличивается и новый раунд не начинается. На границе создаются упорядоченные публичные события `RoundEnded` и, когда применимо, `RoundStarted`.
- **Трассировка:** `RoundEnded` и `RoundStarted` в [событиях движка](packages/game-engine/src/game-events.ts), `advanceTurn` в [lifecycle партии](packages/game-engine/src/game-lifecycle.ts); [интеграционные тесты](packages/game-engine/test/game-lifecycle.test.ts): `начинает новый раунд с первого игрока`, `завершает прежний и начинает новый ход при входе в финальный раунд`, `передаёт ход в финальном раунде`, полные круги для 2–4 участников и `переходы хода и увеличение раунда при первом игроке, отличном от players[0]`; проверены порядок и публичная проекция событий, отсутствие `RoundStarted` при входе в `final_scoring`, глубокая заморозка результата и неизменность входа.

## 7. Условия окончания партии

### END-001 — Три индикатора окончания

- **Источник / фаза / триггер:** конец игры, с. 5; после любого атомарного эффекта, меняющего кассу билетов, статус художника или мешочек посетителей.
- **Условия:** отслеживаются: касса полностью без билетов; не менее двух суперзвёзд; мешочек посетителей пуст.
- **Эффект:** состояние хранит, какие индикаторы уже выполнены.
- **Исключения:** пустая отдельная стопка билетов запускает промежуточный подсчёт, но не равна пустой кассе.
- **События:** `EndConditionReached` для впервые выполненного индикатора.
- **Проверки:** каждый индикатор отдельно; различить пустой цвет билетов и полностью пустую кассу.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — `applyTicketRewardToGameState` после всей награды фиксирует первое опустошение всей кассы в `ticketOfficeEmptyReached` и создаёт `EndConditionReached` после билетных событий и промежуточного триггера, до возможного `GameEndTriggered`. Событие возвращается и без запуска завершения; сохранённый флаг запрещает повтор. `createGame` задаёт `false`, восстановление требует boolean, публичная проекция сохраняет признак. Покупка через `applyArtworkPurchaseToGameState` после всех эффектов также фиксирует переход непустой кассы в пустую и создаёт `EndConditionReached` до возможного `GameEndTriggered`; событие доступно без запуска завершения и в завершающих фазах, сохранённый флаг запрещает повтор. Два остальных индикатора и фиксация после других игровых эффектов ещё отсутствуют.
- **Трассировка:** [команда билетной награды](packages/game-engine/src/ticket-reward-to-game-state.ts), [восстановление снимка](packages/game-engine/src/game-state-validation.ts); [интеграционные тесты](packages/game-engine/test/ticket-reward-end.test.ts) проверяют пустую кассу и отдельный цвет, порядок событий с завершением и без него, обмен последнего билета, завершающие фазы, повторную награду и сохранённое достижение, публичную проекцию, заморозку и атомарные отказы; [тесты восстановления флага](packages/game-engine/test/ticket-office-empty-restoration.test.ts) проверяют оба boolean-значения и отказ для отсутствующего поля и неверных типов. [Команда покупки](packages/game-engine/src/artwork-purchase-payment-state.ts) и [интеграционные тесты покупки](packages/game-engine/test/artwork-purchase-end.test.ts) проверяют первое опустошение после покупки, порядок событий с завершением и без него, отдельный пустой цвет, завершающие фазы, отсутствие повторного достижения, уже пустую кассу, проекцию, восстановление, заморозку и атомарный отказ.

### END-002 — Запуск завершения

- **Источник / фаза / триггер:** конец игры, с. 5; выполнены минимум два индикатора `END-001`.
- **Условия:** партия находится в обычной фазе.
- **Эффект:** фаза один раз переходит из `regular_play` в `ending_current_round`; номер текущего раунда сохраняется в `endTriggeredRound`, первый и активный игроки не меняются.
- **Исключения:** выполнение третьего индикатора не создаёт повторный переход.
- **События:** `GameEndTriggered`.
- **Проверки:** один индикатор не запускает конец; любая пара запускает; повторная оценка идемпотентна.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — общая проверка `canTriggerGameEnd` в модуле жизненного цикла оценивает актуальную кассу билетов, статусы суперзвёзд в `artistMarket.slots` и корневой мешочек посетителей. Явный `triggerGameEnd` разрешает переход из `regular_play` только при минимум двух индикаторах; сохраняет номер раунда, первого и активного игроков и создаёт публичное `GameEndTriggered`. `applyArtworkPurchaseToGameState` автоматически проверяет состояние после всех эффектов покупки и при двух или трёх индикаторах возвращает состояние из `triggerGameEnd`, добавляя его события после событий покупки. При недостатке индикаторов покупка остаётся в `regular_play`; в `ending_current_round` и `final_round` покупка продолжается без повторного запуска. После всей билетной награды `applyTicketRewardToGameState` также оценивает новое состояние через `canTriggerGameEnd` и при необходимости применяет `triggerGameEnd`: билетные ресурсы и промежуточный статус сохраняются, `GameEndTriggered` добавляется после всех событий награды, включая `IntermediateScoringTriggered`. В `ending_current_round` и `final_round` награда не запускает завершение повторно; остальные фазы сохраняют прежнее поведение команды. Переход глубоко заморожен, отказы атомарны. Явный повторный вызов `triggerGameEnd` по-прежнему отклоняется с `Only regular_play`. Сохранение индикаторов по `END-001` и автоматическая оценка после остальных игровых эффектов ещё отсутствуют.
- **Трассировка:** `canTriggerGameEnd` и `triggerGameEnd` в [модуле жизненного цикла](packages/game-engine/src/game-lifecycle.ts), автоматические вызовы в [команде покупки](packages/game-engine/src/artwork-purchase-payment-state.ts) и [команде билетной награды](packages/game-engine/src/ticket-reward-to-game-state.ts), `GameEndTriggered` в [событиях движка](packages/game-engine/src/game-events.ts); [тесты условий окончания](packages/game-engine/test/game-end-conditions.test.ts) проверяют все восемь комбинаций индикаторов и контракт явного запуска; [интеграционные тесты запуска после покупки](packages/game-engine/test/artwork-purchase-end.test.ts) проверяют все три пары и три индикатора, оценку после оплаты билетов, роста известности и пополнения рынка, границу одного индикатора, отличие пустого цвета от пустой кассы, успешные покупки в обеих завершающих фазах без повторного события, порядок событий, публичную проекцию, восстановление, заморозку и атомарный отказ оплаты. [Интеграционные тесты билетной награды](packages/game-engine/test/ticket-reward-end.test.ts) проверяют восемь комбинаций индикаторов после награды, оценку после всех билетов и обмена последнего доступного билета, порядок промежуточного и конечного триггеров, сохранение ресурсов и фазовых полей, отсутствие повторного запуска в обеих завершающих фазах, публичную проекцию, заморозку и атомарный отказ на втором билете. [Тесты жизненного цикла](packages/game-engine/test/game-lifecycle.test.ts) проверяют последовательность завершающих раундов и ограничения фазы; [тест границы движка](packages/game-engine/test/engine-boundary.test.ts) проверяет доступность события игрокам и наблюдателю.

### END-003 — Доигрывание текущего раунда

- **Источник / фаза / триггер:** конец игры, с. 5; вход в `ending_current_round`.
- **Условия:** условие конца могло сработать в ход любого игрока.
- **Эффект:** оставшиеся участники текущего раунда получают обычные ходы до его естественной границы.
- **Исключения:** уже завершившие ход в этом раунде не ходят повторно.
- **События:** обычные события хода; на границе `FinalRoundStarted`.
- **Проверки:** триггер в ход первого, среднего и последнего игрока.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — `advanceTurn` сохраняет круговой порядок в `ending_current_round`, а при возврате к `firstPlayerId` начинает `final_round` и увеличивает номер раунда. Публичное `FinalRoundStarted` возникает ровно один раз между `RoundStarted` и `TurnStarted`, после `TurnEnded`, ожидающего промежуточного дохода и `RoundEnded`. Проверены переходы с разным положением активного игрока относительно первого; игровые действия и остальные отложенные эффекты ещё отсутствуют.
- **Трассировка:** `advanceTurn` в [модуле жизненного цикла](packages/game-engine/src/game-lifecycle.ts), `FinalRoundStarted` в [событиях движка](packages/game-engine/src/game-events.ts); [тесты жизненного цикла](packages/game-engine/test/game-lifecycle.test.ts): «публикует FinalRoundStarted один раз на границе доигрывания» для 2/3/4 игроков с первым игроком не в начале массива, «не публикует FinalRoundStarted внутри доигрываемого раунда», «начисляет промежуточный доход перед FinalRoundStarted без повторного начисления» и «завершает прежний и начинает новый ход при входе в финальный раунд». Проверены точный порядок событий, отсутствие события в обычном и уже начавшемся финальном раундах, проекция для игроков и наблюдателя, неизменность mutable-входа, глубокая заморозка результата и отказ в `final_scoring` без частичных эффектов.

### END-004 — Дополнительный финальный раунд

- **Источник / фаза / триггер:** конец игры, с. 5; завершение раунда из `END-003`.
- **Условия:** начинает первый игрок.
- **Эффект:** каждый участник ровно один раз выполняет обычный ход в круговом порядке.
- **Исключения:** выдворенная фишка возвращается домой, но её владелец не выполняет действие выдворения.
- **События:** `FinalRoundStarted`, обычные события ходов, `FinalRoundEnded`.
- **Проверки:** по одному ходу на игрока; подавление действия выдворения при сохранении возврата фишки.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — реализован один финальный круг от `firstPlayerId` до перехода в `final_scoring`. `advanceTurn` создаёт публичное `FinalRoundEnded` только после последнего финального хода, между `RoundEnded` и `FinalScoringStarted`, после ожидающего промежуточного дохода. Внутри финального раунда событие отсутствует, номер раунда при завершении сохраняется, активный игрок очищается. Составной ход, выдворение и возврат фишек ещё не реализованы.
- **Трассировка:** `advanceTurn` в [модуле жизненного цикла](packages/game-engine/src/game-lifecycle.ts), `FinalRoundEnded` в [событиях движка](packages/game-engine/src/game-events.ts); [интеграционные тесты](packages/game-engine/test/game-lifecycle.test.ts): «публикует FinalRoundEnded только после последнего финального хода для %i игроков» для 2/3/4 участников с первым игроком не в начале массива, «начисляет pending промежуточный доход до перехода в final_scoring», переход к итоговому подсчёту после всех завершающих раундов и передача хода в финальном раунде. Проверены точный порядок событий, публичная проекция для всех игроков и наблюдателя, отсутствие события внутри финального раунда, неизменность mutable-входа, заморозка перехода и событий, отказ повторного вызова из `final_scoring` без частичных эффектов.

### END-005 — Переход к подсчёту

- **Источник / фаза / триггер:** конец игры, с. 5; окончание дополнительного финального раунда.
- **Условия:** все отложенные эффекты последнего хода разрешены.
- **Эффект:** активный игрок очищается, партия переходит в фазу подсчёта; после `SCORE-001`–`SCORE-007` становится завершённой.
- **Исключения:** публичный безусловный переход из обычной игры сразу в `finished` запрещён.
- **События:** `FinalScoringStarted`, позднее `GameFinished`.
- **Проверки:** нельзя завершить обычную фазу вручную; корректная последовательность фаз сохраняет исходное состояние неизменным.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — `advanceTurn` переводит `final_round` в `final_scoring` с публичным `FinalScoringStarted`; после отдельной финальной выплаты за влияние `completeFinalScoring` переводит состояние в `finished`, сохраняет победителей и создаёт в порядке эффектов `WinnerDetermined`, `FinalScoringCompleted` и `GameFinished`. Отложенные эффекты и этапы `SCORE-001`–`SCORE-005` отсутствуют, а показатели `SCORE-007` пока передаются готовыми.
- **Трассировка:** `advanceTurn`, `completeFinalScoring` и `FinishedGameState` в [публичном модуле движка](packages/game-engine/src/index.ts), `FinalScoringStarted` и `GameFinished` в [событиях движка](packages/game-engine/src/game-events.ts); [тесты lifecycle](packages/game-engine/test/game-lifecycle.test.ts) проверяют вход в `final_scoring`, а [интеграционные тесты завершения](packages/game-engine/test/final-scoring-completion.test.ts) — переход в `finished`, порядок итоговых событий, публичную проекцию, глубокую заморозку, восстановление и запрет повторного завершения.

## 8. Действия управления

### MGMT-001 — Выбор и момент действия управления

- **Источник / фаза / триггер:** действия управления, с. 5; собственный обычный ход или разрешённое выдворение.
- **Условия:** в обычный ход доступно не более одного действия управления до или после локации; при выдворении оно является одной из альтернатив.
- **Эффект:** выполняется перемещение посетителей либо получение награды заказа.
- **Исключения:** игрок может отказаться.
- **События:** `ManagementActionStarted` и событие выбранного действия.
- **Проверки:** оба момента обычного хода; отказ; недопустимое второе действие.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no`.

### MGMT-002 — Перемещение посетителей билетами

- **Источник / фаза / триггер:** действия управления, с. 5; выбор перемещения посетителей.
- **Условия:** каждый сброшенный билет соответствует типу перемещаемого посетителя.
- **Эффект:** за билет посетитель движется на один шаг к галерее игрока: площадь→свой вестибюль, свой вестибюль→своя галерея либо чужой вестибюль→площадь. Одного посетителя можно переместить несколько раз за одно действие.
- **Исключения:** движение в обратную сторону и перемещение из любой галереи билетами запрещены; сброшенные билеты не возвращаются в кассу.
- **События:** `TicketSpent`, `VisitorMoved` для каждого шага.
- **Проверки:** допустимые маршруты; два шага одного посетителя; отклонение обратного маршрута и чужой галереи.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no`.

### MGMT-003 — Лимит коллекционеров

- **Источник / фаза / триггер:** действия управления, с. 5; попытка поместить коллекционера в галерею.
- **Условия:** вместимость коллекционеров равна `1 + число проданных игроком произведений`.
- **Эффект:** коллекционер входит в галерею только при наличии свободного места.
- **Исключения:** правило применяется ко всем эффектам перемещения, если конкретный эффект явно не отменяет лимит.
- **События:** обычное `VisitorMoved`.
- **Проверки:** вместимость 1 до первой продажи; рост после продажи; отклонение сверх лимита.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — `advertisingArtist` при награде уровня 5 проверяет лимит `1 + soldArtworkCount` до входа коллекционера. Счётчик создаётся с 0 и сохраняется в схеме 8; первая допустимая награда и атомарный отказ при превышении лимита проверены. Продажа и остальные пути перемещения ещё не интегрированы.
- **Трассировка:** [команда рекламы](packages/game-engine/src/advertising-artist.ts), [восстановление снимка](packages/game-engine/src/game-state-validation.ts); [интеграционные тесты рекламы](packages/game-engine/test/advertising-artist.test.ts): первый коллекционер при нуле продаж, второй при одной продаже, отказ сверх лимита и неизменность счётчика.

### MGMT-004 — Награда карты заказа

- **Источник / фаза / триггер:** действия управления, с. 5; выбор доступной стороны карты заказа.
- **Условия:** на активной стороне карты ещё нет помощника; у игрока есть помощник в офисе или локации. При собственном действии выдворения игрок также может использовать именно своего помощника, выдворенного другим игроком, с клетки выдворения, даже если других доступных помощников нет.
- **Эффект:** помощник помещается на карту, награда её текущей стороны применяется ровно один раз. У всех карт заказов одинаковая оборотная сторона по `ORDER-BACK-001`: выбранная денежная награда даёт 2 монеты за каждого инвестора и 1 монету за каждого коллекционера в своей галерее; выбранная награда влияния даёт 2 влияния за каждую знаменитость и 1 влияние за каждого коллекционера в своей галерее. Состав галереи учитывается при выполнении действия управления, а не при продаже.
- **Исключения:** помощник остаётся на карте до продажи, замены выполненного заказа или иного указанного возврата.
- **События:** `AssistantAssignedToOrder`, события конкретной награды.
- **Проверки:** первая награда; повторное получение запрещено; обратная сторона после продажи может быть активирована отдельно.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no` — все 20 лицевых наград и общий оборот перенесены в 17.5; момент расчёта и допустимые источники помощника утверждены.

## 9. Выдворение и возвращение домой

### EJECT-001 — Выдворение чужой фишки

- **Источник / фаза / триггер:** действия выдворения, с. 6; галерист входит в занятую чужой фишкой локацию.
- **Условия:** целевая фишка — чужой галерист или помощник.
- **Эффект:** фишка переносится на клетку выдворения той же локации; после полного хода активного игрока её владелец получает возможность действия выдворения.
- **Исключения:** следующий обычный ход всё равно принадлежит следующему игроку по кругу.
- **События:** `PieceEjected`, позднее `EjectionOpportunityGranted`.
- **Проверки:** чужой галерист и помощник; возможность появляется только после активного хода.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no`.

### EJECT-002 — Собственный помощник

- **Источник / фаза / триггер:** действия выдворения, с. 6; игрок входит в локацию со своим помощником.
- **Условия:** выдворяется собственная фишка помощника.
- **Эффект:** при наличии свободного рабочего места помощник возвращается в офис; если все четыре места заняты, возвращающийся помощник навсегда удаляется из партии, не попадает в очередь безработных и не может быть нанят повторно.
- **Исключения:** владелец не получает действие выдворения.
- **События:** `OwnAssistantEjected`, затем `AssistantReturnedHome` или `AssistantRemovedFromGame`.
- **Проверки:** возврат без дополнительного действия; полный офис приводит к удалению возвращающегося помощника.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no`.

### EJECT-003 — Альтернативы действия выдворения

- **Источник / фаза / триггер:** действия выдворения, с. 6; предоставлена возможность.
- **Условия:** игрок выбирает не более одной альтернативы.
- **Эффект:** игрок получает не новый обычный ход, а специальное дополнительное действие: либо тратит влияние до предыдущего символа известности и выполняет действие текущей локации, либо выполняет одно действие управления, либо отказывается.
- **Исключения:** обычные предусловия выбранного действия сохраняются.
- **События:** `EjectionActionPerformed` или `EjectionActionDeclined`.
- **Проверки:** обе альтернативы и отказ; недостаточное влияние/недоступное действие.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no`.

### EJECT-004 — Возвращение галериста

- **Источник / фаза / триггер:** действия выдворения, с. 6; завершение возможности выдворенного галериста.
- **Условия:** галерист остаётся на клетке выдворения.
- **Эффект:** галерист возвращается в домашнюю галерею владельца.
- **Исключения:** возврат происходит и при отказе от действия.
- **События:** `GalleristReturnedHome`.
- **Проверки:** возврат после действия и после отказа.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no`.

### EJECT-005 — Возвращение помощника

- **Источник / фаза / триггер:** действия выдворения, с. 6; завершение возможности выдворенного помощника.
- **Условия:** помощник не был использован в выбранном действии.
- **Эффект:** при наличии свободного рабочего места помощник возвращается в офис; если все четыре места заняты, возвращающийся помощник навсегда удаляется из партии, не попадает в очередь безработных и не может быть нанят повторно. Это же правило применяется при продаже работы (`SALE-003`), замене выполненного заказа (`ORDER-003`) и входе на собственного помощника (`EJECT-002`).
- **Исключения:** владелец может использовать именно этого помощника с клетки выдворения в предоставленном ему действии выдворения: поставить на карту заказа или в допустимую ячейку международного рынка, даже при отсутствии помощников в офисе и других локациях. Использованный помощник не возвращается домой. Это разрешение действует при выдворении помощника другим игроком; вход на собственного помощника по `EJECT-002` дополнительного действия не даёт.
- **События:** `AssistantReturnedHome` или `AssistantRemovedFromGame`.
- **Проверки:** свободный офис, полный офис; использование выдворенного помощника на заказе, для репутации и ставки на рынке при отсутствии других помощников; использованный помощник не возвращается; выдворение собственного помощника не предоставляет эту возможность.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no`.

### ARTIST-001 — Доступность открытия художника

### ARTIST-002 — Открытие художника и контракт

- **Источник / фаза / триггер:** сообщество художников, с. 7; успешный `ARTIST-001`.
- **Условия:** выбран допустимый закрытый художник с бонусом, размещённым при подготовке по `SETUP-005`. В корректно подготовленной партии закрытый художник без бонуса невозможен.
- **Эффект:** открыть художника и установить его начальную известность; затем применить и удалить его бонус; для красного художника перенести коллекционера на площадь; поместить одну его подпись на контракт игрока.
- **Исключения:** эффекты выполняются в указанном порядке и атомарно. Если бонус присутствует, но выдаваемый им ограниченный компонент закончился, недоступная награда пропускается по `CORE-002`; художник открывается и остальные эффекты выполняются. Для билетов применяется специальное правило `TICKET-002`.
- **События:** `ArtistOpened`, `ArtistBonusClaimed`, возможное `VisitorMoved`, `ContractSigned`.
- **Проверки:** красный и не красный художник; наличие бонуса у каждого закрытого художника после подготовки; бонус применяется и удаляется ровно один раз; если выдаваемый ограниченный компонент закончился, недоступная награда пропускается, остальные эффекты открытия выполняются.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no` — пользователь подтвердил порядок: открыть художника и установить известность до получения бонуса; ранее согласованные исключения сохраняются.

### ARTWORK-001 — Доступность покупки

- **Источник / фаза / триггер:** сообщество художников, с. 7–8; выбор покупки.
- **Условия:** у художника есть доступная подпись либо его подпись лежит на контракте игрока; в стопке жанра есть работа; в выставочном зале есть доступная перегородка. Художник обязательно открыт; покупка у закрытого художника запрещена.
- **Эффект:** разрешается последовательность `ARTWORK-003`.
- **Исключения:** без контракта нельзя покупать у суперзвезды; обладатель контракта обязан сначала купить работу по контракту; отсутствие обычных подписей не мешает контрактной покупке.
- **События:** отсутствуют до успешного применения.
- **Проверки:** обычная и контрактная покупка; две занятые подписи; суперзвезда; полный зал. Покупка у закрытого художника отклоняется.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — `validateArtworkPurchaseAvailability` проверяет игрока, планшет, открытого художника и работу, вместимость галереи, отсутствие работы того же художника, тип покупки и единственный источник подписи. Проверка вызывается атомарной командой `applyArtworkPurchaseToGameState`; обычная и контрактная подпись, отсутствие подписи и неизменность при отказе проверены интеграционно. Отдельные сценарии продажи последнего шедевра относятся к `ARTWORK-002` и остаются вне среза.
- **Трассировка:** [интеграция покупки](packages/game-engine/src/artwork-purchase-payment-state.ts); [интеграционные тесты](packages/game-engine/test/artwork-purchase-state.test.ts).
- **Граница согласования:** согласованное уточнение взаимодействия зафиксировано в REVIEW-002 (17.11); ранее согласованные части правила сохраняются.


### ARTWORK-002 — Вместимость выставочного зала

- **Источник / фаза / триггер:** покупка и известность, с. 7 и 14; проверка свободного места.
- **Условия:** базово доступны три перегородки.
- **Эффект:** четвёртая доступна только пока в зале находится хотя бы один шедевр.
- **Исключения:** потеря последнего шедевра закрывает четвёртую перегородку; после продажи одной работы в зале остаётся не более трёх работ, поэтому переполнения не возникает.
- **События:** `ExhibitionCapacityChanged` при появлении/исчезновении условия.
- **Проверки:** три обычные работы; четвёртая с шедевром; продажа последнего шедевра.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — полная команда покупки запрещает четвёртую обычную работу без шедевра и любую покупку в полностью заполненную галерею; при трёх обычных работах разрешает контрактную покупку у уже состоявшейся суперзвезды, размещает новую работу как шедевр и создаёт `ExhibitionCapacityChanged` с вместимостью 4. ### ARTWORK-005 — Размещение работы и подписи

- **Источник / фаза / триггер:** покупка, с. 8; после наград.
- **Условия:** доступна перегородка.
- **Эффект:** работа переворачивается и занимает крайнюю левую свободную перегородку. Исключение для третьей выставленной работы: если она является шедевром, она занимает свободную четвёртую перегородку; если четвёртая уже занята другим шедевром, занимает третью. Соответствующая подпись перемещается к делению текущего звёздного рейтинга и определяет текущую цену продажи, которая далее может измениться по `FAME-001`.
- **Исключения:** при контракте используется подпись с клетки контракта. Работа, приобретаемая по контракту у уже состоявшейся суперзвезды, сразу размещается как шедевр; наличие такого шедевра учитывается при определении вместимости по `ARTWORK-002`. Если художник стал суперзвездой в процессе текущей покупки, сама покупаемая работа также сразу размещается как шедевр, независимо от того, была покупка обычной или контрактной.
- **События:** `ArtworkExhibited`, `SignaturePriceSet`.
- **Проверки:** первая и последующая свободная перегородка; третья работа — обычная либо шедевр; свободная четвёртая перегородка и четвёртая, занятая другим шедевром; контракт очищается; цена соответствует рейтингу после увеличения известности.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — полная команда покупки сохраняет `ExhibitedArtwork`, переносит выбранную подпись из общего запаса либо контракта, очищает использованный контракт, вычисляет цену после роста известности и выбирает крайнюю левую позицию с исключением для третьей работы-шедевра. Обычная, контрактная и специальная четвёртая позиция проверены интеграционно; все комбинации уже занятой четвёртой позиции ещё не покрыты.
- **Трассировка:** типы `Gallery`, `PlayerContract` и `ExhibitedArtwork` в [планшетах игроков](packages/game-engine/src/player-boards.ts), [атомарная интеграция покупки](packages/game-engine/src/artwork-purchase-payment-state.ts), [интеграционные тесты](packages/game-engine/test/artwork-purchase-state.test.ts).
- **Граница согласования:** согласованное уточнение взаимодействия зафиксировано в REVIEW-001 (17.11); ранее согласованные части правила сохраняются.


### ARTWORK-006 — Обновление рынка и стартовая репутация

- **Источник / фаза / триггер:** покупка, с. 8; работа снята с вершины стопки.
- **Условия:** купленная работа снята с вершины стопки. Получение стартовой репутации проверяется независимо от наличия следующей работы в стопке.
- **Эффект:** если в стопке есть следующая работа, на неё помещаются следующие посетители из детерминированно подготовленного порядка `visitorBag` по числу напечатанных билетов, насколько позволяет мешочек. Когда в галерее появляется третья выставленная работа, стартовый жетон репутации с третьей перегородки переносится на эту работу, в том числе если шедевр размещён на четвёртой перегородке по `ARTWORK-005`. Жетон остаётся на работе до конца хода, затем переносится на свободную клетку репутации игрока и приносит награду этой клетки. После получения жетона игрок обязан вернуть одного выбранного посетителя из своего вестибюля на площадь, если посетители есть.
- **Исключения:** если в момент получения свободной клетки репутации нет, стартовый жетон теряется и удаляется из партии. Пустой вестибюль не препятствует получению жетона и награды клетки; перемещение посетителя пропускается. Не активированный к финальному подсчёту стартовый жетон удаляется. Один стартовый жетон не может быть получен повторно.
- **События:** `ArtworkMarketRefilled`, возможные `ReputationTokenClaimed`, `BoardRewardClaimed`, `VisitorMoved`.
- **Проверки:** полный/частично пустой мешочек; последняя работа в стопке не блокирует стартовую репутацию; появление третьей обычной работы и третьего произведения-шедевра на четвёртой перегородке; перенос жетона сначала на работу, затем в конце хода на планшет; потеря при отсутствии клетки; обязательный возврат посетителя при наличии; получение при пустом вестибюле.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — чистое пополнение рынка интегрировано в `applyArtworkPurchaseToGameState`: следующая работа и посетители сохраняются в `artworkMarket`, корневой `visitorBag` расходуется, а пустая стопка оставляет открытую позицию `null`, сохраняет мешочек и не создаёт `ArtworkMarketRefilled`. При появлении третьей работы команда снимает стартовый жетон с перегородки и сохраняет связь его ID с ID купленной работы в `reputationTokenArtworkIds`, включая шедевр на четвёртой позиции и последнюю работу рынка. Связь видна в публичной проекции, новых событий на этом этапе нет. Перенос на клетку репутации в конце хода, награда клетки, возврат посетителя и удаление жетона остаются вне среза.
- **Трассировка:** `refillArtworkMarket` в [модуле пополнения рынка](packages/game-engine/src/artwork-market-refill.ts), [атомарная интеграция покупки](packages/game-engine/src/artwork-purchase-payment-state.ts); [модульные тесты](packages/game-engine/test/artwork-market-refill.test.ts), [интеграционные тесты покупки](packages/game-engine/test/artwork-purchase-state.test.ts) и [переноса стартового жетона](packages/game-engine/test/artwork-starting-reputation.test.ts): третья обычная работа и шедевр на четвёртой позиции, независимость от пополнения рынка, сохранение жетона до третьей работы, отсутствие повторного переноса при пустой перегородке, публичная проекция, восстановление, заморозка, неизменность входа и отказ покупки.

### ORDER-002 — Обновление области заказов

- **Источник / фаза / триггер:** отдел продаж, с. 9; начало действия получения заказа.
- **Условия:** игрок ещё не выбрал карту. По явному решению пользователя обновление разрешено не более одного раза в отдельном действии получения заказа. Раскрытие неизвестной информации требует подтверждения до выполнения; успешное обновление сохраняется и не откатывается при последующем отказе от карты.
- **Эффект:** игрок может выложить четыре новые карты поверх текущих слева направо; старые остаются под ними; после обновления игрок может не брать карту.
- **Исключения:** если перед обновлением в колоде осталось меньше четырёх карт, переработка выполняется до первого добора. Набор собирается в устойчивом порядке: сброс в порядке массива; непустые верхние карты позиций 1–4; нижние слои позиций 1–4, каждый от самой нижней карты к ближайшей к верху; оставшаяся колода в порядке добора. Все эти карты перемешиваются потоком `orders/recycle` по `ADR-008`; первые четыре карты заполняют позиции слева направо, остаток сохраняется в колоде, сброс и нижние слои очищаются. Если в собранном наборе меньше четырёх карт, команда атомарно отклоняется до обращения к RNG.
- **События:** `OrderMarketRefreshed`, возможное `OrderDeckRecycled`; начало самостоятельного действия и отказ после обновления возвращают пустой массив событий.
- **Проверки:** через публичную receiveOrder проверены WAITING → REFRESH → REFUSAL, продолжение восстановленного PENDING, отсутствие трёх внутренних команд в публичном API, отказ повторного обновления и обновления из REFUSAL/SUCCESS, отказ DECLINE до обновления и повторного отказа, отказ ACCEPT_ORDER без выбора, передача состояния и событий обычного обновления и переработки при остатке 0–3 карты, сохранение области и RNG при отказе, скрытая проекция, схема 12, неизменность и заморозка. Недостаток карт атомарно сохраняет входной WAITING либо PENDING. Регрессионные тесты внутренних функций сохраняют проверки порядка набора, сохранности карт, ровно четырёх карт всего, детерминизма, независимости счётчиков, повторных переработок и переполнения счётчика.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — публичная receiveOrder(state, playerId, typeAction) объединяет самостоятельное начало и продолжение действия. Обычное обновление сохраняет нижние слои и возвращает OrderMarketRefreshed; при остатке 0–3 карты предварительная переработка возвращает OrderDeckRecycled → OrderMarketRefreshed. DECLINE из REFRESH сохраняет область и RNG, устанавливает REFUSAL и возвращает events: []; ACCEPT_ORDER с полным выбором поддерживает ограниченный путь ORDER-003 из PENDING и REFRESH; без выбора и из REFUSAL/SUCCESS отклоняется. changeStatusPlayer, actionOrderMarket и refreshOrderMarket исключены из публичного API, поэтому самостоятельное обновление в обход контроля этапа недоступно через него. Снимок схемы 12 сохраняет этап; схемы 10–11 отклоняются. Получение без обновления и после REFRESH, раскрытие нижней карты и билет первой пустой клетки реализованы ограниченным срезом ORDER-003. ### MARKET-005 — Размещение ставки

### INFLUENCE-002 — Получение монет через влияние

- **Источник / фаза / триггер:** влияние, с. 13; непосредственная оплата покупки, найма или ставки.
- **Условия:** игрок перемещает маркер назад как минимум до предыдущего символа монеты.

- **События:** `InfluenceSpent`, `CoinsReceived`, затем `CoinsSpent`.
- **Проверки:** покрыть дефицит; использовать влияние при наличии собственных монет; запрет свободной конвертации; переход с 1 влияния к 0 даёт одну монету для платежа; стоя на 0, повторное получение недоступно.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — позиции денежных символов и монета за достижение нулевого символа подтверждены пользователем. Чистый расчёт и неизменяемое применение расхода реализованы; покупка работы принимает допустимую цель влияния даже при достаточном числе собственных монет, атомарно сохраняет итоговые ресурсы в `GameState` и создаёт по порядку `InfluenceSpent`, `CoinsReceived`, `CoinsSpent`. Оплата найма также интегрирована через applyAssistantHiringToGameState и проверена в assistant-hiring-state.test.ts; контекст ставки ещё не интегрирован.
- **Трассировка:** `calculateCoinsFromInfluenceSpend` в [модуле расхода влияния на монеты](packages/game-engine/src/influence-spending.ts), `spendInfluenceForImmediatePayment` в [модуле применения расхода влияния](packages/game-engine/src/influence-spending-award.ts) и `applyArtworkPurchasePaymentToGameState` в [интеграции оплаты покупки](packages/game-engine/src/artwork-purchase-payment-state.ts); [тесты расчёта](packages/game-engine/test/influence-spending.test.ts), [тесты применения](packages/game-engine/test/influence-spending-award.test.ts) и [интеграционные тесты покупки](packages/game-engine/test/artwork-purchase-payment-state.test.ts): покрытие дефицита, добровольная конвертация при достаточных монетах, переход к 0, порядок и публичная проекция событий, отклонение неверной цели, атомарность и неизменяемость.

### TICKET-002 — Замещение отсутствующего цвета

- **Источник / фаза / триггер:** билеты, с. 13–14; требуемая цветная стопка кассы пуста.
- **Условия:** в кассе есть билет другого цвета и в сбросе есть требуемый цвет.
- **Эффект:** один билет другого цвета из кассы уходит в сброс, затем требуемый билет берётся из сброса.
- **Исключения:** если вся касса пуста, билет нельзя взять непосредственно из сброса: игрок не получает билет, запасы кассы и сброса не меняются. Если требуемого цвета нет ни в кассе, ни в сбросе, игрок также не получает билет; билет другого цвета остаётся в кассе и не сбрасывается.
- **События:** `TicketExchanged`, `TicketReceived`.
- **Проверки:** замена; полностью пустая касса; требуемого цвета нет ни в кассе, ни в сбросе — билет не выдаётся, запасы кассы и сброса не меняются, события обмена и получения не создаются.
- **Статус:** `spec: approved` · `implementation: yes` · `tests: yes` — `replaceUnavailableTicket` разрешает обмен только при наличии другого билета в кассе и требуемого билета в сбросе; публичная команда применяет результат к кассе, сбросу и билетам игрока и создаёт `TicketExchanged` перед `TicketReceived`. Полностью пустая касса и отсутствие требуемого цвета в сбросе оставляют запасы без изменений и не создают событий.

### MID-001 — Единственный промежуточный подсчёт

- **Источник / фаза / триггер:** промежуточный подсчёт, с. 14; в кассе впервые опустела любая одна цветная стопка.
- **Условия:** промежуточный подсчёт ещё не проводился.
- **Эффект:** при триггере подсчёт только назначается. В конце текущего обычного хода, после действий выдворения и их отложенных эффектов, перед ходом следующего игрока каждый получает 2 влияния за знаменитость, 1 влияние за коллекционера, 2 монеты за инвестора и 1 монету за коллекционера в своей галерее. Учитывается состав галерей на момент начисления, включая изменения во время действия выдворенного игрока.
- **Исключения:** последующее опустошение других цветов повторного подсчёта не вызывает. Если первая стопка опустела во время действия выдворения, подсчёт проходит в конце этого же обычного хода, до следующего игрока. При отсутствии действий выдворения назначенный подсчёт выполняется после остальных эффектов конца хода.
- **События:** `IntermediateScoringTriggered`, по одному `IntermediateIncomeAwarded` на игрока.
- **Проверки:** первый пустой цвет; повторный пустой цвет; точные награды для смешанного состава галереи; отсутствие немедленного дохода при назначении; перемещение посетителей выдворенным игроком влияет на последующее начисление; триггер во время выдворения разрешается в том же обычном ходе; подсчёт при отсутствии выдворения.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: partial` — первое опустошение цветной стопки билетной наградой через `applyTicketRewardToGameState` или покупку произведения однократно переводит сохраняемый `intermediateScoringStatus` из `not_triggered` в `pending` и публикует `IntermediateScoringTriggered` после всех билетных событий, не начисляя доход немедленно. `advanceTurn` получает актуальный состав посетителей из галерей, применяет готовый расчёт ко всем игрокам, создаёт по одному `IntermediateIncomeAwarded`, сохраняет `completed` и размещает начисление после `TurnEnded`, но до следующего хода, границы раунда либо `FinalScoringStarted`. Путь назначения во время ещё не реализованного выдворения остаётся вне доступного рабочего сценария.
- **Трассировка:** `calculateIntermediateIncome` в [модуле расчёта промежуточного дохода](packages/game-engine/src/intermediate-income.ts), `applyIntermediateIncomeToPlayer` и `applyIntermediateIncomeToPlayers` в [модуле применения промежуточного дохода](packages/game-engine/src/intermediate-income-award.ts); назначение через [билетную награду](packages/game-engine/src/ticket-reward-to-game-state.ts) и [атомарную покупку](packages/game-engine/src/artwork-purchase-payment-state.ts), исполнение в конце хода через `advanceTurn` в [lifecycle партии](packages/game-engine/src/game-lifecycle.ts), поле статуса в [типах состояния](packages/game-engine/src/types.ts), [публичная проекция](packages/game-engine/src/game-projection.ts) и [runtime-валидация](packages/game-engine/src/game-state-validation.ts); [интеграционные тесты lifecycle](packages/game-engine/test/game-lifecycle.test.ts) проверяют смешанный состав галерей, однократность, порядок относительно следующего хода, границы раунда и финального подсчёта, публичную проекцию событий, неизменяемость и атомарный отказ при несогласованных планшетах. ### FAME-001 — Рост и цена работ

- **Источник / фаза / триггер:** известность, с. 14; покупка или реклама.
- **Условия:** художник открыт.
- **Эффект:** текущая известность определяет цену обычной покупки; при достижении следующего звёздного рейтинга все подписи уже приобретённых работ этого художника перемещаются к новой цене продажи.

### SCORE-002 — Лидерство на международном рынке

- **Источник / фаза / триггер:** финальный подсчёт, с. 15; первый этап.
- **Условия:** по каждой используемой колонке считаются все помощники игрока в верхней и нижней частях.

- **События:** `MarketLeadershipScored`.

### SCORE-003 — Жетоны репутации и выставка

- **Источник / фаза / триггер:** финальный подсчёт, с. 15 и справочник с. 20.
- **Условия:** у каждого игрока находится не более одного жетона репутации на планшете; работы находятся в выставочных залах.

- **Исключения:** порядок между несколькими жетонами одного игрока не требуется, поскольку владеть более чем одним жетоном нельзя; игрок без жетона пропускает этот шаг.

- **Проверки:** каждый тип жетона отдельным параметризованным сценарием; игрок без жетона; запрет состояния с несколькими жетонами у одного игрока; несколько работ разных художников.

### SCORE-004 — Аукцион выдающихся произведений

- **Источник / фаза / триггер:** финальный подсчёт, с. 15; этап аукциона.
- **Условия:** ставка игрока равна сумме значений рядов его помощников в нижней части рынка: 1, 3 или 6 за помощника. К аукциону допускаются только игроки с положительной ставкой; игроки с нулевой ставкой не получают работы.
- **Эффект:** игроки по убыванию ставки выбирают по одной доступной выдающейся работе, пока работы не закончатся; работа прикладывается к одной выбранной карте цели — куратора либо арт-дилера — и может помогать её выполнению. Игрок немедленно получает её цену как цену работы самого известного открытого художника того же жанра; если открытых художников этого жанра нет, цена равна 0. Полученная аукционная работа учитывается в числе всех приобретённых работ при разрешении ничьей по `SCORE-007`.
- **Исключения:** один игрок получает не более одной работы; ничья разрешается большей ставкой в колонке 3, затем 2, затем 1. При полном равенстве всех трёх значений связанные игроки получают приоритет выбора по обычной очередности хода: от `firstPlayerId` по круговому порядку `players`. Если работ меньше, раньше стоящий в этом порядке выбирает раньше, а последний связанный игрок может остаться без работы.
- **События:** `AuctionResolved`, `ExceptionalArtworkAwarded`, `CoinsReceived`.
- **Проверки:** разные ставки; все уровни разрешения ничьей; полное равенство значений колонок при `firstPlayerId`, не совпадающем с `players[0]`; игроков больше, чем работ; ограничение одной работы; недопуск нулевой ставки, даже если остаются работы; цена 0 при отсутствии открытых художников жанра; выбор карты куратора или арт-дилера.
- **Статус:** `spec: approved` · `implementation: no` · `tests: no` — при полном совпадении ставок порядок выбора ограниченных работ определяется обычной очередностью хода от `firstPlayerId`.

### SCORE-005 — Карты целей

- **Источник / фаза / триггер:** финальный подсчёт, с. 15; после аукциона.
- **Условия:** известны приобретённые, выставленные, проданные и полученные на аукционе работы.
- **Эффект:** карта куратора начисляет монеты за указанные коллекции выставленных работ и не более одной аукционной работы. Карта арт-дилера начисляет монеты за указанные наборы проданных работ; приложенная к ней аукционная работа также может помогать выполнению целей. Одна аукционная работа прикладывается только к одной из двух карт и не учитывается одновременно для обеих; само приложение к карте арт-дилера не является продажей.
- **Исключения:** конкретные цели и суммы задаются данными карт. На каждой карте работа расходуется при оплате строки или набора и не может использоваться повторно в другой строке либо наборе этой же карты — одинаково для куратора и арт-дилера. Каждая строка цели арт-дилера оплачивается за каждый отдельный полный набор работ; например, строка «две скульптуры → 10 монет» при четырёх разных проданных скульптурах даёт 20 монет.
- **События:** `CuratorCardScored`, `DealerCardScored`.
- **Проверки:** каждая карта и цель; запрет повторного использования работы в строках куратора и арт-дилера; два отдельных набора из двух скульптур дают 20 монет, неполный набор не оплачивается; ограничения аукционной работы; использование на карте арт-дилера; запрет одновременного учёта на обеих картах.
- **Статус:** `spec: approved` · `implementation: partial` · `tests: yes` — неизменяемые данные всех восьми карт и общий запрет повторного использования работ перенесены и протестированы; вычисление очков, учёт аукционной работы и интеграция с финальным подсчётом отсутствуют.
- **Трассировка:** `curatorGoals` и `dealerGoals` в [каталоге карт целей](packages/game-engine/src/goal-card-catalog.ts); [тесты](packages/game-engine/test/goal-card-catalog.test.ts): состав карт, строки `CURATOR-01`/`DEALER-01`, общий запрет повторного использования и глубокая заморозка.

### SCORE-007 — Разрешение ничьей

- **Источник / фаза / триггер:** финальный подсчёт, с. 15; несколько лидеров по монетам.

- **Проверки:** первое размещение напротив; последующее круговое движение; нейтральный соперник не выполняет обычное действие локации.

### SOLO-003 — Выдворение и рынок нейтрального соперника

- **Источник / фаза / триггер:** одиночная игра, с. 16; выдворение или вход нейтрального соперника на рынок.

- **Статус:** `spec: deferred` · `implementation: no` · `tests: no`.

### SOLO-004 — Окончание и цели

- **Источник / фаза / триггер:** одиночная игра, с. 16; касса полностью без билетов.

### 17.4. Произведения — все 44 видимых экземпляра

`ANY` — один билет любого цвета; `DIFF2` — два любых билета разных цветов; `R+(B/W)` — розовый и один коричневый либо белый; `B+(R/W)` — коричневый и один розовый либо белый; `B+R+W` — по одному каждого цвета; `—` — билетов нет. Число посетителей на верхней работе равно количеству напечатанных билетов, а не количеству разрешённых цветов.

`n+C` — напечатанный прирост известности n плюс число коллекционеров покупателя в галерее. `X` — вместо всей формулы напечатан крестик: это не подменяется формулой `0+C`. Для всех четырёх работ X пользователь подтвердил: известность не растёт, коллекционеры не добавляют прироста и дополнительная известность за влияние при этой покупке запрещена.
